## 1. 适合 Cardfolio 的科技感

### 1.1 定义

Cardfolio 的科技感应被定义为：**用户能感知系统在可靠地整理复杂金融规则，并把下一步行动、证据和结果讲清楚。** 它是操作确定感，不是视觉炫技。

具体表现为五个可观察的信号：

1. **状态协议清楚**：逾期、临期、待核对、已达标、结果待确认、处理中和已完成有独立层级，用户在 1 秒内知道先处理什么。
2. **数据有新鲜度**：余额、规则、活动资格和来源都显示最后核对时间；“待核对”是可信度维度，不被误读成系统错误。
3. **数字有工具感**：金额、积分、日期、次数和进度使用 tabular numerals，并以稳定列对齐；比较不依靠装饰卡片。
4. **材质有空间逻辑**：画布、实心数据面、提升面和浮动 Chrome 分层；半透明说明“这是悬浮结构”，不会把核心数据变成玻璃噪声。
5. **反馈有因果和恢复**：点击立即有按下反馈；保存显示对象、新值和结果；失败保留输入；可恢复操作提供撤销；动效可中断且不阻塞高频维护。

因此，Cardfolio 的科技感更接近“高质量个人运营工具”或“可核对的轻量指挥台”，而不是 AI 研究实验室、交易终端或消费金融营销页。

### 1.2 反模式

| 反模式 | 为什么不适合 Cardfolio | 评审处理 |
| --- | --- | --- |
| 全屏紫色/青蓝渐变、霓虹光晕 | 把品牌色当作可信度，稀释状态语义；长期使用疲劳 | 禁止作为画布和大面积面板背景 |
| 全页面玻璃化、卡片套卡片 | 背景透出导致中文和数字对比不稳定；层级变平 | 只允许侧栏、顶栏、抽屉、浮层使用半透明 |
| 扫描线、粒子、动态网格、呼吸光点 | 把维护工具游戏化；增加视觉运动和 CPU 成本 | 禁止循环装饰；网格如保留必须静止且极弱 |
| “AI 预测”“智能建议”“置信度分数” | 暗示产品验证银行资格或提供金融建议，超出数据边界 | 使用“记录、比较、待核对、来源等级” |
| 大号数字墙、指标卡瀑布 | 让用户先看总量而不是待办；工作台变成展示页 | 首屏按风险、行动、概况排序 |
| 每个对象都使用彩色状态胶囊 | 状态颜色泛滥，无法分辨活动、权益、积分和年费 | 生命周期、可信度、时间紧迫度分轴表达 |
| 过度等宽字体或终端化文案 | 中文正文和复杂规则阅读疲劳；显得仿制开发工具 | 只在金额、积分、日期、键位提示使用数字对齐 |
| 过长弹簧、入场级联、键盘操作动画 | 高频动作有延迟感；动效成为完成任务的门槛 | 高频操作 120–220ms；键盘触发不加装饰动画 |
| 深色默认但没有打印、对比度、减弱透明度退化 | 造成疲劳和无障碍失败；数据无法可靠导出 | 深色必须和浅色共享语义 token 与结构 |
| 仅靠 hover、颜色或图标表达结果 | 移动端无 hover，屏幕阅读器无法得到上下文 | 文字状态、可访问名称、焦点和结果播报必须完整 |

## 2. 对工作台原型的总体判断

`design-prototypes/cardfolio-command-center.html` 的方向是成立的：石墨画布、蓝灰实心数据面、轻度透明侧栏/顶栏、青蓝行动色、琥珀/珊瑚风险色，已经符合“材料有边界”和“状态优先”的基本思路。它也明确禁止全屏渐变、粒子和循环扫描线，这一点应保留。

但它目前更像“视觉方向稿”，还不是可直接通过的产品原型，原因有三类：

- **产品语气偏强**：`command center`、实时新鲜度点和发光状态线容易让个人维护工具显得像自动监控系统；需要在文案和动效上降低“实时智能”的暗示。
- **交互证据不足**：原型主要演示静态导航和时间窗切换，尚未证明来源核对、任务修正、权益使用、兑换处理中/失败等关键状态可恢复。
- **正式样式尚未统一**：当前 [app/globals.css](/Users/chenyixing/Project/xyk管理/app/globals.css:2353) 已有浅色语义 token、侧栏/顶栏 `backdrop-filter`、`prefers-reduced-transparency`、`prefers-contrast` 和 `prefers-reduced-motion`；原型的深色 token 需要作为同一套语义系统的主题，而不是另起一套组件视觉。

最终评审应按“方向可接受，但必须通过下列 10 条准则”处理，而不是以“看起来像 AI 产品”作为通过条件。

## 3. 原型最终评审的 10 条准则

### 1. 一眼完成优先级识别

在桌面 1440 × 900 和移动 390 × 844 首屏，用户应能区分：逾期、7 天内临期、待核对、普通待办和已完成。状态不能只靠发光点；每条队列项必须有对象类型、中文状态、截止日/相对时间和下一步动作。

**证据**：使用同一组混合数据走查 5 秒遮挡测试；遮住标题后仍可通过状态文字和结构判断紧迫度，遮住颜色后仍可完成排序。

### 2. 工作台不是指标墙

首屏顺序必须是“待处理队列 → 近期时间线 → 任务/资产摘要”，指标仅作为可下钻的摘要条。每个摘要都能进入预设筛选列表，不能只显示大数字。

**证据**：从工作台开始，用户在不打开全局搜索的情况下完成一项临期任务；主流程不超过 2 次导航动作。

### 3. 半透明只表达结构层

液态玻璃只能用于侧栏、顶栏、移动导航抽屉、浮层和需要与内容分离的检查器。任务表、积分批次、时间线、表单和权益使用记录保持实心数据面；同一视图不叠两层半透明表面。

**证据**：开启 `prefers-reduced-transparency: reduce` 后，内容层级、边界、焦点和状态仍清晰；关闭 blur 不应改变信息架构。

### 4. 深色模式不制造“实时智能”假象

深色主题可以有静止的极弱网格、细线边界和有限状态光晕，但不得使用实时扫描、自动闪烁、动态粒子或未经数据支持的“在线/同步中”信号。数据最后核对日期必须比装饰性 fresh dot 更重要。

**证据**：断开网络或使用陈旧数据时，页面清楚显示“最后核对”与“待核对”，不会继续显示类似实时系统的绿色在线指示。

### 5. 数字比较稳定且中文可读

金额、积分、日期、次数、百分比使用 tabular numerals；标题、规则和来源正文使用系统中文字体。任何数字都同时说明单位和语义：当前值、目标值、剩余值、待入账值、估算值或已确认值。

**证据**：用 `¥12,000 / ¥20,000`、`4 / 6 次`、`12,000 分，8 月 21 日到期` 等最长真实数据走查，不能截断单位或把 pending 当成已达标。

### 6. 视觉重点不覆盖可信度信息

青蓝、琥珀、珊瑚和绿色只作为行动/风险/完成语义，不作为银行品牌装饰。来源等级、规则版本、最后核对时间和适用渠道必须有固定位置，不能被大号标题或彩色状态 chip 推到详情深处。

**证据**：活动、权益和任务列表在 1 次展开内能看到来源等级与最后核对时间；来源缺失时出现“待核对”，而不是空白或默认“官方”。

### 7. 快捷动作具备完整的处理中和回退态

“更新进度”“记录使用”“记录兑换”“确认到账”都必须有按下、处理中、成功、失败和重试状态。失败保留原输入；重复点击不产生两条记录；可恢复动作提供撤销。兑换未到账不得提前扣减确认余额，权益使用失败不得先扣次数。

**证据**：模拟网络超时、重复点击、服务端 500、兑换退款和任务冲正；原始记录、草稿、数值和时间线均可重算。

### 8. 桌面与移动是同一流程的不同容器

桌面右侧检查器只承载单一短任务；复杂建档、规则版本对比、跨对象影响预览进入完整页面。移动底部抽屉承载相同字段和校验，固定主操作避开软键盘与安全区，关闭后恢复触发元素焦点。

**证据**：同一对象在桌面和 390 px 移动端使用相同 URL、筛选、字段、状态和历史；只改变检查器/抽屉容器，不出现移动端专属的第二套业务逻辑。

### 9. 动效服务空间关系，不服务炫技

按钮按下约 100–160ms；抽屉/侧栏约 180–240ms，使用明确 ease-out 或可中断 spring；进度更新只做一次短促宽度过渡。键盘触发的重复操作不播放装饰动画。所有可拖拽表面应 1:1 跟随手势并继承释放速度，边界有渐进阻力。

**证据**：慢放检查进入/退出路径、transform-origin、速度交接和反向抓取；`prefers-reduced-motion: reduce` 改为淡入/颜色反馈，无位移和弹性。

### 10. 视觉通过必须包含可访问性与真实内容验证

不得用漂亮的占位短文本通过评审。必须使用真实中文长标题、来源摘录、长银行名、金额/积分和错误信息测试 360 px、390 px、1280 px、1440 px 及 200%/400% 文字缩放。状态、焦点、标签和错误可被键盘与屏幕阅读器理解。

**证据**：完成键盘 Tab/Enter/Escape、VoiceOver 或 NVDA、`prefers-contrast: more`、`forced-colors: active`、`prefers-reduced-transparency` 和 `prefers-reduced-motion` 走查；不能以截图代替交互证据。

## 4. 深色命令台与浅色 Liquid Glass 的选择

### 4.1 推荐：浅色为默认，深色为系统主题/专注模式

对 Cardfolio，我不建议把深色命令台设为唯一默认，也不建议将浅色仅视为“无障碍降级”。推荐如下：

| 场景 | 推荐主题 | 理由 |
| --- | --- | --- |
| 工作台默认进入 | 浅色 Liquid Glass | 个人财务工具需要长时间阅读、录入和核对；浅色对中文、表单和打印更稳 |
| 需要集中处理临期任务 | 深色专注模式 | 深色可提高状态轨道、截止日和来源提示的聚焦度，但仍使用实心数据面 |
| 卡片详情、规则、来源原文 | 浅色 | 长文本、表单和字段对比更舒适，可信度不被发光效果干扰 |
| 提醒队列、活动/任务执行 | 两者均可 | 共享同一状态 token；深色仅提升对比，不改变语义 |
| 导出/打印/高对比/减弱透明度 | 浅色实心退化 | 确保材料退化后信息与层级仍完整 |

主题选择应优先跟随系统 `prefers-color-scheme`，同时提供用户手动切换；不要根据“紧急程度”自动切换主题。自动切换会改变空间记忆，也会让用户误以为系统进入了特殊风险状态。

### 4.2 为什么不选择单一深色默认

- Cardfolio 不是实时同步的银行终端，深色命令台会过度承诺“实时”和“智能”。
- 长段中文规则、来源摘录和表单在深色下需要更高的正文对比度和更严谨的灰阶；原型目前尚未提供这些文本验证。
- 深色的青蓝、琥珀、珊瑚光晕如果同时出现，会把每个对象都变成“警报”，削弱真正逾期项。
- 浅色已经存在于 [app/globals.css](/Users/chenyixing/Project/xyk管理/app/globals.css:2354) 的语义变量中，沿用现有结构成本更低；深色应建立在相同变量语义上，而不是另起组件。

### 4.3 Liquid Glass 的边界

Liquid Glass 不是“透明卡片风格”。Cardfolio 只采用以下可落地部分：

- `backdrop-filter: blur()` 和半透明背景只用于悬浮 Chrome；
- 通过内亮边、细分隔线和阴影表达表面厚度；
- 浮层进入时同时 materialize blur、opacity 和轻微 scale，退出沿相同来源路径返回；
- `prefers-reduced-transparency` 时改为不透明实色；
- 内容数据面保持不透明，确保对比度、打印和扫描。

禁止把每个指标、每条任务、每个积分批次都做成漂浮玻璃小卡，也禁止在玻璃层上叠玻璃层。

## 5. 可落地到现有页面的视觉重点

以下是设计评审对现有页面的优先级，不是本轮代码改动清单。实现时应优先复用现有语义 class 和 token，不在业务组件内复制颜色。

### P0：先修“工作感”，再修装饰

| 现有页面/选择器 | 视觉重点 | 通过标准 |
| --- | --- | --- |
| `.app-frame`、`.content`、`.dashboard-grid` | 建立明确 L0 画布、L1 数据面、L2 提升面的纵向节奏；减少同权重白色块 | 工作台首屏有明确风险→行动→概况顺序，内容区不显得像卡片堆 |
| `.metrics`、`.metric` | 从五个同权重指标改为摘要条或主次分组；每个数字可下钻 | “待处理”与“未来 90 天”视觉优先，普通总数不抢主焦点 |
| `.section-block`、`.side-panel`、`.event-row` | 实心数据面统一边界和内边距；避免容器套容器 | 列表行、时间线和积分批次能对齐扫描，只有当前/异常面使用提升面 |
| `.card-row`、`.fee-row`、`.reminder-row` | 增加稳定的对象类型、状态、关键日期和下一步列；状态文字不只由 chip 表达 | 1440 px 能快速横向比较；390 px 自然转语义行，不截断操作 |
| `.progress-line`、`.progress-track` | 区分已确认、待入账、有争议和目标；轨道不使用连续发光动画 | `当前 / 目标 / 剩余` 在同一视觉组内，进度不会被误读为银行确认 |
| `.status-pill`、`.overdue-pill`、`.nav-count` | 降低胶囊和颜色的权重；同一对象分开显示生命周期、可信度、时间紧迫度 | 关闭颜色后仍能通过文字识别状态；只给真正逾期使用高风险色 |
| `.topbar`、`.sidebar`、`.sidebar-scrim` | 保留半透明 Chrome，但确保内容滚动时有稳定边界和实色 fallback | blur 不可用、减弱透明度或高对比模式下布局和可读性不变 |
| `.modal`、`.modal-detail`、`.modal-backdrop` | 卡片详情从长模态升级为深链页面；模态只承载新增/确认/单一短任务 | 桌面有检查器或完整详情，移动有底部抽屉；关闭后焦点可恢复 |
| `.calendar-day`、`.event-list` | 日历点、颜色块只做索引；详情列表提供完整日期、对象、状态和下一步 | 月视图不能成为唯一事件信息；移动列表无横向溢出 |
| `.toast`、`.form-error`、`.form-success` | Toast 只做即时补充；页面内保留成功新值、错误原因、重试和撤销 | 网络失败时输入不丢，成功播报包含对象和结果，而非仅“已保存” |

### P1：增加身份与精致度

- **品牌位**：保留现有简洁 mark，不引入旋转 3D logo 或大面积发光；可以用一条静止的语义色内亮边区分品牌，但不要让 logo 成为最大视觉焦点。
- **数字排版**：现有 body 已设置 `font-variant-numeric: tabular-nums`，应确保金额、积分、日期和进度组件继承，而中文标题不被强制等宽化。
- **状态轨道**：在待处理行或积分批次行首使用 2px 轨道，比整块彩色背景更有科技感且更可扫描；轨道旁必须保留文字状态。
- **来源新鲜度**：在活动、权益、任务、积分详情头部固定一行“来源等级 · 最后核对日期”；不要用绿色在线点代替证据。
- **层级阴影**：数据面使用极轻控制阴影，抽屉/模态使用更深 overlay shadow；不要给每一行都加独立阴影。
- **按钮反馈**：保留 Emil 建议的 `scale(.97–.98)` 按下反馈，但只作用于可点击控件；列表行不要因 hover 改变尺寸。
- **空状态**：用对象图标、原因和一个明确动作，避免空状态变成装饰性大插画；“没有待办”应说明下一关键日期或维护动作。
- **真实内容**：用长银行名、长活动名、规则摘录、金额和错误文案做验收，不能用 Lorem ipsum 或过短占位文本评价密度。

### P2：主题与高级质感

- 共享 light/dark 语义 token；主题只改变画布、材料和边界色，不改变状态含义、间距、组件顺序或中文文案。
- 为深色主题增加实心数据面、正文对比度、选择态边界和打印 fallback；没有这些前置条件不把深色设为默认。
- 为浮层加入 materialize 过渡：`opacity + transform + blur` 同步，且从触发点产生；不使用 `scale(0)`。
- 为移动抽屉采用可中断位移和速度交接；低动效模式改为淡入，不把手势变成唯一关闭方式。
- 仅在有真实数据意义的地方使用微弱光晕，例如当前焦点、待处理计数或进度轨道；不做背景氛围动画。

## 6. 最终评审所需的验收证据

视觉评审不能只看一张桌面截图。原型最终交付应同时提供：

1. 1440 × 900 工作台：混合逾期、临期、待核对、处理中和正常数据。
2. 390 × 844 工作台：长中文标题、软键盘打开的底部抽屉和安全区。
3. 1280 px 中间宽度：验证双栏坍缩与右侧时间线，不允许出现过窄列。
4. 浅色、深色、`prefers-reduced-transparency`、`prefers-reduced-motion`、`prefers-contrast: more` 和 `forced-colors: active` 六种视图或等价录屏。
5. 活动报名失败、权益使用失败、任务退款/冲正、积分批次不一致、兑换处理中/失败/退款五个异常操作的录屏或走查记录。
6. 键盘 Tab/Enter/Escape 路径、焦点恢复、屏幕阅读器状态播报和错误定位证据。
7. 慢放检查 180–240ms 抽屉/浮层动画，确认 enter/exit 路径对称、transform-origin 正确、反向抓取无跳变。
8. 内容密度检查：最长银行名、活动名、来源摘要、金额、积分和错误文案在 200% 与 400% 缩放下不遮挡、不截断关键动作。

截图只能证明视觉状态，不能证明提交、失败恢复、焦点或动效可中断；交互证据必须包含实际操作。

## 7. 待验证问题

1. 用户是否把“深色命令台”理解为自动同步或银行实时状态，而不是手动记录工具。
2. 浅色 Liquid Glass 在多模块首屏中是否仍能让逾期和待核对状态于 1 秒内脱颖而出；若不能，应加强状态轨道和摘要分组，而非把全页面变深。
3. 原型中的实时新鲜度点是否会与“最后核对日期”产生冲突；建议只有在有明确后台同步事实时才使用“同步中”语言。
4. 深色下中文正文、来源摘录和表格辅助文字是否达到 WCAG AA；不能只用 token 理论值，需要浏览器实测。
5. 右侧检查器的最大信息量是多少；规则来源、影响预览和错误摘要一旦超过一屏，应自动转完整详情页。
6. 390 px 底部抽屉中，中文大字号、日期输入、固定操作和错误摘要是否会形成双层滚动。
7. 用户能否区分“预计占用积分”和“已确认扣减”，以及权益使用失败后剩余量未变化的反馈是否足够明显。
8. 工作台是否需要记住用户的主题选择，还是始终跟随系统；建议记住手动选择，并提供恢复系统设置。
9. 是否需要为高频 keyboard shortcut 提供无动画 command palette；若加入，快捷动作应使用明确的可访问名称，不称为 AI 助理。

## 8. 结论与交付边界

建议通过另一个 UX 原型的**结构方向**，有条件通过其**视觉方向**：

- 通过石墨画布 + 实心数据面 + 轻度透明 Chrome 作为可选主题骨架；
- 不通过全站深色默认、实时/智能暗示、未验证的光效和只展示静态状态的演示；
- 正式产品默认采用浅色 Liquid Glass 或跟随系统，深色作为可切换的专注模式；
- 先完成工作台优先级、状态协议、来源新鲜度、异常恢复和跨端一致性，再增加高级材质。

当前 CSS 已有可复用基础：系统中文字体、语义色 token、`backdrop-filter` fallback、短促 easing、焦点环、移动 44 px 触控目标以及三类偏好媒体查询。实现阶段应在这些基础上统一主题变量，而不是为原型复制一套独立 CSS。
