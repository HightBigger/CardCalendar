## 1. 结论与能力边界

当前代码可作为年费 MVP 基线验收：已有账号、卡片档案、年费周期/事件、手动进度流水、年费提醒、导出和账户删除相关 API、领域测试及两条 Playwright 主流程。当前可见 API 包括 `/cards`、`/cycles`、`/progress-entries`、`/fee-events`、`/reminders` 和 dashboard。

工作台 PRD、架构、UX 与数据库文档规划了卡活动、权益、刷卡方式/任务、积分账户与批次、兑换、规则版本和来源快照，但当前代码、迁移和测试中没有这些完整聚合或 API。因此本文件中的测试分为：

- **现有基线**：当前代码必须持续通过的年费能力。
- **规划 P0/P1**：需求签署后才进入实现，测试用例先作为开发契约。
- **发布阻断项**：缺失时不能宣称对应工作台版本可部署。

本轮没有执行修改；文档只基于仓库静态检查和现有契约编写。

## 2. 测试分层与统一约定

### 2.1 测试层级

| 层级 | 目标 | 推荐工具/证据 |
| --- | --- | --- |
| 领域单元 | 状态机、日期、金额/积分运算、剩余量、版本迁移、冲正 | Vitest；固定时钟、属性/表格测试 |
| 应用服务 | 所有权、命令幂等、审计、事务边界和错误码 | Vitest + fake repository；重复请求/并发测试 |
| API 契约 | 请求校验、`404/409/422`、分页、`Idempotency-Key`、旧 API 兼容 | Supertest 或 Next route contract tests |
| PostgreSQL 集成 | 外键、唯一约束、事务回滚、`numeric` 精度、索引和用户隔离 | 临时 PostgreSQL；迁移后 DDL smoke/rollback |
| Worker/可靠性 | outbox/inbox 去重、重试、死信、提醒生成和读模型新鲜度 | pg-boss 测试；故障注入和重跑 |
| E2E/UI | 从录入到结果确认的主流程、空/错/处理中状态和导航恢复 | Playwright，桌面 1280/1440 与移动 360/390 |
| 安全/隐私 | IDOR、日志/导出脱敏、速率限制、来源附件权限 | 集成安全用例、静态扫描、人工检查 |

### 2.2 通用测试规则

1. 测试数据必须带 `user_id`、用户 IANA 时区、来源可信状态和 `provenance`；不得用前端传入的新余额覆盖账本派生余额。
2. 金额用十进制定点断言；积分用整数或计划声明的最小单位。禁止用二进制浮点相等断言。
3. 每个可重试命令保存请求哈希和结果；相同幂等键相同请求返回同一结果，复用同一键但请求不同返回冲突。
4. 所有历史事实只追加，错误用 reversal/adjustment；规则编辑产生新版本，不覆盖已引用版本。
5. 断言状态文字、图标/形状和颜色三者的组合；不能只断言颜色。
6. 测试失败时保留 request/correlation ID、聚合版本、时区、source/rule version 和数据库快照，便于复现。

### 2.3 建议固定夹具

| 夹具 | 关键值 |
| --- | --- |
| 用户 A | `Asia/Shanghai`，3 张卡；一个年费任务、一个活动、一个共享积分账户 |
| 用户 B | `America/Los_Angeles`，与 A 使用相同资源 ID 的攻击请求 |
| 金额边界 | `0.00`、`0.01`、`999999999999.99`、三位小数、负数、不同币种 |
| 时间边界 | 截止日 00:00/23:59、闰日、月末、夏令时跳变、用户改时区 |
| 规则版本 | 生效前 draft、当前 active、已过期、superseded、needs_review 并存 |
| 失败注入 | 数据库超时、唯一键冲突、worker 重复消费、外部来源不可访问、通知投递失败 |

## 3. 领域测试矩阵

### 3.1 卡活动（CardActivity / Campaign / Enrollment）

| 场景 | 预期 | 优先级/状态 |
| --- | --- | --- |
| 创建活动，填写起止时间、报名截止、适用多张卡、渠道/地区/排除项和来源 | 字段保存；活动显示 `planned`/`running`；每个卡片关联可追溯 | P0 规划 |
| `start_at` 等于 `end_at`、报名截止早于开始、时区带来的跨日 | 拒绝非法区间；明确使用用户时区解释，不静默改日期 | P0 规划 |
| 无报名要求、未开始、已报名、报名失败、名额未知/已满 | 参与状态与活动生命周期独立展示；名额不足不能标为可参加 | P0 规划 |
| 未确认资格、适用卡不匹配、地区/渠道不符 | 显示“资格待确认/不适用”及原因；不能推断奖励 | P0 规划 |
| 活动奖励仅有文字、上限或分段奖励 | 保留原文和 `reward_amount_text`；只有用户确认且来源明确才进入数值汇总 | P0 规划 |
| 活动完成但奖励未到账 | 活动可为“已达标”，奖励结果为“待确认”；不提前增加积分/收益 | P0 规划 |
| 活动过期后补录结果 | 允许补录历史，禁止新报名；原规则版本保持不变 | P0 规划 |
| 重复提交关注/报名、网络重试 | 幂等返回同一 enrollment；不得重复创建任务或事件 | P0 规划 |
| 规则版本替换 | 新报名引用新版本；进行中/已完成实例继续引用旧版本并显示变更提示 | P0 规划 |
| 用户 A 读取/修改用户 B 活动 | 统一 `404`；不泄露标题、银行名或存在性 | P0 规划 |

| 场景 | 预期 | 优先级/状态 |
| --- | --- | --- |
| 录入次数型、额度型、无限次、一次性权益 | 正确显示单位、周期、有效期/重置日；无限次显示“次数不限” | P0 规划 |
| 使用量为 0、等于上限、超过上限、负数或小数精度不符 | 0 和等于上限合法；超过/负数拒绝或进入待确认，不得出现负剩余 | P0 规划 |
| 记录使用、取消/回退、重复提交 | 使用记录不可变；回退产生 reversal；相同幂等键不重复扣减 | P0 规划 |
| 预约/激活要求、地区、同行人、渠道限制 | 详情和列表都显示限制；未完成预约不能标“可用” | P0 规划 |
| 权益从 `available` 到 `partially_used/exhausted/expired/revoked` | 仅允许架构定义的状态转换；过期后只读但可补记实际结果 | P0 规划 |
| 估算价值与实际价值 | 分开存储和展示，估算不计入已确认净值；币种和计算依据必填 | P0 规划 |
| 规则缺来源、来源过期或冲突 | 标记 `needs_review`/来源存疑；不计入“可用权益”总数 | P0 规划 |
| 归档卡片 | 停止未来新提醒/新任务，历史权益使用和估值仍可读 | P0 规划 |

### 3.3 刷卡方式与刷卡任务（SpendMethod / SpendTask）

| 场景 | 预期 | 优先级/状态 |
| --- | --- | --- |
| 计数、金额、`count_and_amount`、`count_or_amount`、custom 任务 | 当前/目标/剩余和逻辑关系正确；custom 只能显示说明并要求用户确认 | P0 规划 |
| 起止日相等、结束早于开始、目标为 0、极大目标 | 合法边界有明确语义；非法区间/溢出拒绝 | P0 规划 |
| POS、电商、移动支付、二维码、境外、自动扣款等方式 | 方式、商户/MCC、地区、币种和排除项可独立记录；未知保留 `unknown` | P0 规划 |
| 追加增量与设置累计值 | 两种模式在 UI/API 明确区分；累计值由流水重算，客户端不能任意写派生值 | P0 规划 |
| 负向退款/冲正、撤销错误流水 | 原记录保留，反向记录关联 `reversal_of_entry_id`；完成度可下降并留审计 | P0 规划 |
| 金额币种不一致、金额 0、金额两位以上小数 | 拒绝或要求显式换算；不自动使用汇率；金额按 `numeric(14,2)` 计算 | P0 规划 |
| 同时满足/满足其一 | 仅满足任一条件时 `any` 达标；`all` 必须全部达标；进度显示最短板 | P0 规划 |
| 附属卡是否计入、指定商户/渠道排除 | `yes/no/unknown` 显示在规则摘要；unknown 不得判定银行已认可 | P0 规划 |
| 任务暂停、恢复、取消、过期 | 只允许定义的状态迁移；暂停不丢失已有流水，取消后不得继续写入 | P0 规划 |
| 重复记录/并发追加 | 幂等键和乐观锁避免双计；版本冲突返回 `409` 并可重新加载 | P0 规划 |
| 当前代码年费进度基线 | `calculateProgress` 拒绝负数/非有限值，金额保留两位，计数与金额同时满足取较低进度；追加值可重算 | 现有基线 |
| 当前代码缺口 | 现有 `ProgressRule` 只覆盖 none/count/amount/count_and_amount；已有年费流水撤销，但无通用活动任务、消费方式/渠道、原始退款关联字段、custom/any | 发布前明确限制 |

### 3.4 积分账户、批次与不可变流水

| 场景 | 预期 | 优先级/状态 |
| --- | --- | --- |
| 多银行、多计划、多单位账户；同银行多卡合并池 | 账户独立于卡片；关联卡可空；单位不混算 | P0 规划 |
| 余额手动录入、账单/App 核对、调整 | 保存 `balance_as_of`、来源和核对时间；余额是快照/投影，流水可重放 | P0 规划 |
| earn/redeem/expire/adjust/transfer/reversal | 类型和来源完整；历史只追加；冲正不删除原流水 | P0 规划 |
| 批次到期：未知、固定日期、滚动、lot-based | 未知有效期不生成日期或提醒；仅对明确 `expires_on` 生成提醒 | P0 规划 |
| 批次剩余量为 0、部分使用、过期、作废 | `open/partially_used/used/expired/void` 与流水汇总一致；禁止负剩余 | P0 规划 |
| 流水重放与余额快照不一致 | 显示对账差异和最后计算时间；不静默修正用户快照 | P0 规划 |
| 积分小数/大数/精度 | 使用整数或计划最小单位；超范围、非法小数拒绝；避免浮点误差 | P0 规划 |
| 账户冻结/关闭 | 冻结禁止新兑换但可查看/调整（按策略）；关闭保留历史并停止到期提醒 | P0 规划 |
| 用户 A 读取/调整用户 B 账户或批次 | `404`，不返回余额或来源 | P0 规划 |
| 当前代码能力 | 没有 points account/lot/ledger 表、路由或测试 | 尚未实现 |

### 3.5 兑换（Redemption）

| 场景 | 预期 | 优先级/状态 |
| --- | --- | --- |
| 计划中、已提交、处理中、成功/到账 | P0 只记录外部兑换状态；到账后由用户确认并以兑换 ID 幂等生成扣减流水 | P0 规划 |
| 资格、渠道、库存、客户/卡种上限未知或不满足 | 详情显示限制；不能伪造“可兑换”或推荐排序 | P0 规划 |
| 所需积分为 0、现金补差 0、两位小数、负数、超余额 | 0 的语义明确；负数/超余额拒绝；现金补差按金额精度校验 | P0 规划 |
| 并发两次确认同一兑换/扣减 | 兑换 ID 与幂等键保证一次业务效果；系统内 reservation/事务锁属于 P1/P2 | P0/P1 规划 |
| 提交/履约失败、取消、退款、重试 | 失败可重试；已扣积分必须 release/reversal；失败不能静默删除记录 | P0 规划 |
| 重复点击提交/确认到账 | `redemption_id` + `Idempotency-Key` 保证一次业务效果；重复返回原状态 | P0 规划 |
| 当前代码能力 | 无 redemption 表、路由、积分 reservation 或履约 worker | 尚未实现 |

### 3.6 来源可信度与规则版本

| 场景 | 预期 | 优先级/状态 |
| --- | --- | --- |
| 官方规则、官方商品页、官方商城、第三方、用户自录 | 来源等级可见；详情有 URL/标题/访问日期/原文摘录 | P0 规划 |

## 4. 横切测试矩阵

### 4.1 金额、积分和精度

| 检查 | 验收标准 |
| --- | --- |
| 数据库类型 | 金额为 `numeric(14,2)`；积分为整数或计划最小单位；无浮点列 |
| 输入校验 | 空值、负数、NaN、Infinity、科学计数法、超过 14 位精度均有明确错误；前后端校验一致 |
| 汇总 | 以十进制定点聚合；`0.10 + 0.20 = 0.30`；累计、冲正和重放结果一致 |
| 币种 | 币种不一致拒绝或要求用户提供已确认换算；不自动抓实时汇率 |
| 舍入 | 活动积分取整、银行入账规则来自 RuleVersion；没有规则时显示未知 |
| 导出 | JSON/CSV 保留精确值、币种、单位、来源日期和估算/确认标记 |

### 4.2 日期、时区和周期

| 检查 | 验收标准 |
| --- | --- |
| 存储 | 瞬时事件使用 `timestamptz`，纯日历日期使用 `date`；接口明确 ISO 格式 |
| 提醒 | 在用户时区按本地日期计算提前节点，再转换发送时间；同一节点不因 DST 重复/跳过 |
| 边界 | 截止日当天 00:00 与 23:59、月末、闰年 2 月 29 日、跨年周期均有测试 |
| 改时区 | 已生成提醒显示原时区和时间；只重排未来通知，历史发生时间不改写 |
| 过期 | 到期后只读保留历史；补录需标记补记时间，不重开旧周期 |
| 当前基线 | 已有固定日期/闰日领域测试与 Asia/Shanghai 提醒 09:00 测试；活动/积分时区尚无实现 |

### 4.3 权限、隐私和审计

| 检查 | 验收标准 |
| --- | --- |
| 所有权 | 每个查询/命令从会话取得 `user_id`；跨用户 ID 统一 `404`，不泄露存在性 |
| 敏感输入 | 完整卡号、CVV、密码、银行凭据、敏感 URL 参数被拒绝或脱敏；仅允许 last4 |
| 角色边界 | 用户只能修改自己的实例；未来管理员模板与用户报名/估值权限分离 |
| 状态写入 | 状态只能由聚合 owner 修改；跨模块通过 port/事件，禁止直写他表 |
| 审计 | 创建、编辑、报名、使用、记账、兑换、规则确认、归档、导出、删除、重试均记录 actor、版本、来源、request/correlation ID |
| 删除/归档 | 归档保留历史并取消未来提醒；账户删除可撤销冷静期/匿名化按策略执行，导出不含秘密 |

### 4.4 幂等、并发、失败重试

| 检查 | 验收标准 |
| --- | --- |
| 命令重放 | 相同键 + 相同请求返回原结果；相同键 + 不同请求返回冲突；无键的重复写被限流或拒绝 |
| 并发 | 同一任务/权益/积分账户的写入使用乐观锁或事务锁；不重复扣减、不产生负余额 |
| 事件消费 | inbox 以 `(consumer,event_id)` 去重；乱序事件不重复记账，未知版本可安全拒绝/隔离 |
| Worker 重试 | 指数退避、最大次数、死信和告警；通知失败不回滚业务事实，兑换失败可补偿 |
| 事务 | 跨事实写入要么全部提交要么全部回滚；故障注入后可重跑并恢复一致状态 |
| 读模型 | 返回 `as_of`/stale 标记；最终一致期间显示处理中，不把旧数据写成实时余额 |
| 提醒 | 自然键为对象 + 节点 + 类型；`insert ... on conflict do nothing`，归档/达标取消未来提醒 |

### 4.5 移动端、可访问性和视觉状态

| 检查 | 验收标准 |
| --- | --- |
| 视口 | 360、390、768、1280、1440 px；无横向滚动、表格可转卡片/横向滚动且不裁切关键字段 |
| 触控 | 主按钮和列表操作最小 44 px；底部抽屉、导航抽屉、模态框支持 Escape/返回和焦点恢复 |
| 状态 | 逾期/待核对/处理中/失败同时用文字、图标/形状和颜色表达；对比度符合 WCAG AA |
| 加载/错误 | 骨架尺寸稳定；局部重试不清空其他内容；表单错误保留已填值 |
| 键盘/读屏 | 表单 label、错误、对话框标题和状态可读；焦点顺序合理；非颜色信息可感知 |
| 动效 | 支持 `prefers-reduced-motion`、`prefers-reduced-transparency`、高对比度；动效中断不改变数据 |
| 当前基线 | 已有移动端 MVP E2E、模态框焦点、导航抽屉和中文 UI 检查；工作台新页面尚不存在 |

## 7. 验证方式与未决问题

### 7.1 验证方式

- 每个状态表采用合法/非法转换表格测试；每个金额和日期边界使用参数化测试。
- 使用固定时钟和至少 `Asia/Shanghai`、`America/Los_Angeles` 两个时区；在 DST 前后和跨日边界执行提醒 worker。
- 使用临时 PostgreSQL 执行迁移、约束、并发锁、事务回滚、备份恢复和 RLS/ownership 测试。
- Playwright 使用桌面/移动视口、网络离线/恢复、重复点击和刷新恢复 URL；截图作为视觉回归证据。
- 运行静态敏感信息扫描，检查日志、导出、错误响应和 source snapshot 是否出现完整卡号/CVV/token。

### 7.2 未决问题（实现前必须定稿）

1. DBA 文档 `DATABASE-WORKBENCH.md` 已落盘；进入实现前仍需将其表名、约束和迁移顺序与最终 API/领域契约逐项冻结。
2. PRD 的活动 `CardActivity` 与架构的 `Campaign/Enrollment` 是一对一还是模板与个人实例分离，需明确测试对象和权限边界。
3. “设置累计值”如何映射为不可变流水、如何避免导入与人工记录重复，需定义命令协议和幂等键生成规则。
4. 积分计划的最小单位、取整规则、批次分配（FIFO/用户指定）及账户余额不等时的对账策略尚未确定。
5. 权益是否在 P0 提供完整使用流水，还是先保留可审计的简化记录；若简化，需明确补偿和并发限制。
6. 提醒活动/权益/积分节点的默认时间、免打扰和送达失败策略尚未实现；需确定“逾期”是查询派生还是持久化状态。
7. 规则来源原文/附件保存期限、加密方式、恶意文件扫描和删除策略需经安全角色确认。
8. 当前应用为个人租户；未来共享工作台引入 `workspace_id` 后，必须新增角色/资源策略和跨租户测试，不能沿用单用户假设。
