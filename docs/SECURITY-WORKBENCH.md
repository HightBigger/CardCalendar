## 1. 结论与安全边界

Cardfolio 的正确安全定位是个人金融相关信息的**最小化记录工具**，不是银行账户聚合器、交易执行器或资格裁决系统。工作台扩展可以在不保存完整卡号和银行凭据的前提下上线手工记录能力，但以下边界必须保持明确：

1. 用户的“已报名”“已达标”“可使用”“兑换成功”是其手工记录或已确认事实，不是系统对银行结果的承诺。
2. 每个业务对象都归属于一个个人用户；引用卡片、活动、积分账户、规则、来源和附件时，服务端必须在同一授权上下文验证它们属于同一用户。
3. 余额和资格不可由客户端直接改写。积分、权益次数和刷卡任务进度应由可追溯的命令和不可变流水/反向流水派生。
4. 附件、PDF、截图、导入文件、来源网页内容和未来同步数据都是高风险输入，不能按普通表单文本处理。
5. P0 仅允许手工录入；P1 导入必须经历隔离、预览、逐项确认和可撤销，P2 第三方同步须另行安全与合规评审。

本文件将“当前已具备能力”与“工作台实现前要求”严格分开。后者是设计与发布门槛，不能被表述为已经上线的保护措施。

### 2.2 当前能力与缺口

| 控制项 | 当前基线已实现 | 工作台缺口与上线含义 |
| --- | --- | --- |
| 会话与密码 | Argon2 密码哈希；32 字节随机会话令牌只存 SHA-256 哈希；Cookie 为 `HttpOnly`、`SameSite=Lax`，生产环境加 `Secure`。 | 没有会话新鲜度/再次验证机制；报名、兑换、导出、授权撤销等高影响命令需要定义二次确认或近期登录策略。 |

| 已有幂等 | 年费事件和提醒依靠自然键/唯一索引避免重复生成；进度支持反向记录。 | 没有通用 `Idempotency-Key` 存储、账户版本号、积分账本或兑换 reservation。活动报名、权益核销、积分调整、兑换都不能复用当前年费任务的有限幂等保护。 |
| 限流 | 登录、注册、导出、删除使用单实例内存固定窗口限流。 | 多实例部署不能依赖内存限流；活动/兑换/导入/附件上传需自己的配额和分布式限流。 |

| 文件、导入、同步 | 无文件上传、来源快照、CSV/PDF 导入或银行同步实现。 | 所有相关安全控制均为未来要求，未完成前不得以“支持凭证/导入/同步”对外发布。 |

### 2.3 当前风险结论

当前年费 MVP 的安全控制可作为手工工作台的基础，但不能直接承载积分账本、附件或自动化导入。特别是“当前 API 已鉴权”不等于新关联资源天然安全；“当前提醒有唯一索引”也不等于兑换扣点具有幂等性。

## 3. 数据分级与最小化

### 3.1 数据类别

| 级别 | 数据 | 处理原则 |
| --- | --- | --- |
| 限制级 | 密码、会话令牌、刷新令牌、OAuth 授权码/访问令牌、银行登录信息、完整卡号、CVV/CVC、PIN、短信验证码、身份证件。 | 永不写入业务表、日志、审计、分析、来源正文、导出或附件。银行密码和验证码没有例外。 |
| 敏感级 | 邮箱、卡片后四位、账单/兑换订单号、权益使用凭证、截图、交易日期与金额、积分余额、兑换明细、银行 App 页面。 | 仅在实现功能所需时收集；按用户隔离、传输和静态加密、短期保留、访问留痕；导出前显式确认。 |
| 业务级 | 发卡行、卡产品名、规则文字、活动时间窗、渠道/地区、任务目标、积分单位、规则来源 URL、可信度与核对时间。 | 保存结构化最小字段和来源摘要；外部内容不作为可信代码或可执行 HTML。 |
| 公开级 | 已脱敏的产品帮助文本、无用户参数的公开规则链接。 | 仍禁止把用户报名状态、持卡关系或个人兑换结果暴露给其他用户。 |

### 3.2 强制禁止项

以下内容必须在客户端提示、服务端校验、日志/分析脱敏和导入扫描中同时阻止；仅靠产品文案不够：

- 完整 PAN、卡磁道数据、CVV/CVC、PIN、有效期组合、银行登录密码、短信/动态验证码、网银 UKey 内容。
- OAuth access token、refresh token、授权码、Cookie、`Authorization` 头、连接器原始响应。
- 身份证、护照、银行卡正反面、包含完整卡号的账单/截图、含二维码支付凭证的原件。
- 与卡片管理无关的完整交易明细、精确地理位置、通讯录、短信或邮件全文。

`last4` 只能是四位数字。订单或参考号只保留实现去重/核对所需的脱敏尾号、哈希或用户自定义备注；禁止把“订单号字段”当作可无限制粘贴的敏感文本入口。

### 3.3 字段最小化规则

- **活动报名**：保存状态、用户确认时间、适用卡引用、规则版本和可选的脱敏参考号；不保存银行页面会话、账户姓名或报名页原始 HTML。
- **权益凭证**：默认只保存使用日期、使用量、渠道和简短说明。仅在争议核对确有需要时允许 P1 附件，并以“辅助证据”而非资格结论呈现。
- **刷卡方式与手工记录**：P0 记录汇总次数/金额、日期、方式和备注，不要求商户名称、商品、位置或原始账单。备注限制长度、纯文本化和敏感模式提醒。
- **积分与兑换**：保存积分单位、数量、批次有效期、状态及最小参考信息；余额必须标明 `as_of`、来源类型和用户确认状态，不能伪装为实时银行余额。
- **来源快照**：优先存 URL、标题、访问时间、摘要、哈希、解析器版本和脱敏摘录。原始文件/正文只在导入或争议排查必要时短期加密保存。

## 4. 威胁模型

### 4.1 资产、信任边界与攻击者

**核心资产**：用户账户和会话、卡片关联关系、活动报名和权益使用历史、手工消费汇总、积分账本、兑换状态、来源快照/附件、导出数据、审计记录、未来连接器令牌。

**信任边界**：浏览器与 API、应用与数据库、应用与对象存储/病毒扫描、导入解析沙箱、应用与外部规则站点、连接器与第三方 API、后台 worker 与业务数据库、备份与恢复环境。

**主要攻击者**：未登录的互联网攻击者、已登录但试图读取或修改他人数据的用户、被 XSS/恶意浏览器扩展影响的用户会话、恶意或误操作的导入提供者、含恶意内容的来源站点、被盗的部署/对象存储凭据，以及重复投递/重放请求的网络或 worker 故障。

## 5. 授权、所有权与状态变更

### 5.1 通用授权规则

1. API 从当前会话取得 `actor_user_id`，请求体中不得接受或覆盖 `owner_user_id`。
2. 所有读、写、下载、导出、撤销和后台重试均以 `actor_user_id` 作为首要过滤条件。后台 worker 使用受限的系统身份，并在 job payload 中仅传资源 ID 与必要的用户 ID。
3. 创建关联对象前，在一个事务内验证其父级链路。例如，`SpendTask.card_id`、`activity_id`、`rule_version_id` 和 `source_snapshot_id` 必须同属当前用户或为公开只读模板；`Redemption.account_id` 与可选 `card_id` 必须相互兼容并同属当前用户。
4. 不存在和无权访问返回相同的 `404`。不要返回“该资源属于其他用户”或用权限错误枚举 UUID。
5. 任何未来共享能力必须引入独立 `workspace_id`、成员和资源策略；不得在当前 `cards` 上加一个共享布尔字段来绕过个人隔离模型。

### 5.2 卡活动报名与资格

活动规则与个人报名是不同对象：可复用的规则/模板不能因被用户引用而获得编辑其个人状态的权限。

- `ActivityEnrollment` 只能由活动适用卡的所有者创建、取消或确认；应固定关联 `rule_version_id`、`source_snapshot_id`、时间窗和 `provenance`。
- 建议状态为 `not_started -> submitted -> confirmed | failed | cancelled | needs_review`，其中 `confirmed` 还应带 `confirmation_basis`（用户确认/银行页面确认/未知），而不是单一“成功”。
- `enrollment_deadline`、地区、渠道、客群和名额是规则提示，不能当作服务端对用户资格的判断依据。超时或规则变更必须转为待核对，不能在后台把用户状态自动改为已获资格。
- 对“报名”“领取”“取消报名”等可重试命令强制幂等键、版本号和审计；不可让浏览器重放或 worker 重试重复登记。

### 5.3 权益使用与凭证

权益领取（entitlement）与权益使用（usage/redemption）应分别建模。一次使用记录应包含权益实例、日期、数量、渠道、可选脱敏说明、录入来源和关联规则版本；每次修改都应以修正/作废记录表达。

- P0 不接收附件，也不以“填写了使用量”认定银行已经核销。
- P1 仅接受明确允许的图片/PDF 子集；对象存储必须私有，数据库只保存对象 ID、内容哈希、扫描状态、大小、媒体类型、保留到期时间和最小化元数据。
- 上传后先处于 `quarantined`，扫描与内容检查通过后才为 `available`；扫描失败、超时或类型不符时不提供预览/下载。
- 对展示图片使用受控转换副本或安全响应头，不直接以用户上传内容作为同源 HTML/SVG。下载使用 `Content-Disposition: attachment`，访问链接单次或短时有效，且每次重新验证所有权。
- 设计中应允许“删除凭证但保留已发生使用的脱敏审计事件”，并让用户看到保留期限。

### 5.4 刷卡方式、任务与用户手工记录

刷卡方式只描述渠道或规则口径，不能成为保存完整交易的借口。`SpendEntry` 是用户手工记录，不是银行账单。

- 手工记录的金额/次数、日期和币种由服务端验证；金额使用 decimal/numeric，禁止 JavaScript 浮点累计与客户端传入 `remaining_*`/`qualified`。
- 只允许将方式、活动、任务、规则版本和卡片关联到同一用户。卡片归档/关闭后，新记录默认拒绝或显式进入只读纠错流。
- `manual`、`imported_pending`、`imported_confirmed`、`bank_confirmed` 等 provenance 不可由普通用户任意提升。P0 仅允许 `manual`；状态显示必须反映证据等级。
- 编辑不覆盖历史事实：可用修正或 reversal 保留原因、原事件 ID 和操作者。对同一业务日期的重复记录提供提示，但不得默默合并。
- 备注只按纯文本渲染，限制长度和换行/控制字符；不以 HTML、Markdown HTML 或公式解释用户输入。

### 5.5 积分账本、兑换与幂等

积分是最需要防止重复写入和覆盖的工作台领域。余额是账本投影，不是客户端可写字段。

1. `PointsEntry` 设计为追加式流水，包含账户、类型、数量、发生/入账时间、来源、规则版本、关联对象和 reversal 引用。更正通过反向流水实现。
2. `PointsAccount.balance` 仅是投影：在同一数据库事务中以账本重算或按序号维护；服务端拒绝客户端上传的“新余额”。
3. 兑换使用状态机，例如 `planned -> submitted -> reserved -> fulfilled | failed | cancelled | refunded`。任何积分扣减必须同时绑定 `redemption_id` 和命令幂等记录。
4. 创建/确认兑换时锁定积分账户投影或使用可验证的乐观版本；余额不足、账户冻结或版本过期返回可恢复错误。对每个账户设置非负余额约束/对账检查，异常时冻结进一步扣减。
5. 同一 `Idempotency-Key` + 同一用户 + 同一命令 + 同一请求哈希重复到达，必须返回第一次已提交的结果；同键不同 payload 返回 `409 IDEMPOTENCY_KEY_REUSED`。键不可跨用户复用。
6. 不因用户记录“submitted”就扣减最终积分；若业务需要预留，预留应是独立、可到期释放的账本事件。退款/失败不得删除历史流水。

## 6. 审计、日志和脱敏

### 6.1 审计事件最低字段

工作台写命令应写入 `actor_type`、`actor_id`、`user_id`、动作、资源类型/ID、目标版本、请求/关联 ID、结果、发生时间和最小化的字段级变更摘要。对于规则和导入，额外记录 `rule_version_id`、`source_snapshot_id`、`import_batch_id`、行号及 parser version；对于兑换，记录 `redemption_id`、账本 entry ID 和幂等命令 ID。

审计内容应支持调查“谁在何时基于哪个规则版本做了什么”，而不是复制整个请求或文件。审计事件必须可追加、受访问控制且保留删除/匿名化语义；普通用户只能读取自己的时间线，运营/系统角色只能读取经批准的最小范围。

### 6.2 脱敏规则

- 日志、错误报告、分析埋点、队列 payload、审计 `metadata` 均采用字段白名单，不使用“整包 JSON 序列化后再祈祷脱敏”。
- 屏蔽或哈希 token、Cookie、认证头、密码、验证码、完整卡号、邮箱本地部分、原始 IP、附件路径、来源页面查询参数和完整订单号。
- 对卡号只允许展示 `**** 1234`；订单号默认展示末 4--6 位；导出和 UI 的掩码规则一致。
- 生产错误响应仅返回稳定错误码、用户可理解消息和 `request_id`，详细异常堆栈只进入受控日志且仍需脱敏。
- 在 CI、预发布和运行时增加敏感模式扫描，至少拦截 13--19 位连续数字、CVV 语义字段、`Authorization`、`Cookie`、token 和密码键名进入日志/审计/导出。模式命中应进入人工复核，不应把疑似敏感原文再次打印出来。

### 6.3 现有审计的改造要求

当前审计基础可复用，但必须在扩展前补充统一 `AuditWriter`/schema 验证和元数据白名单。不能由每个新 service 自由写入任意 JSON；否则来源摘录、附件 URL、订单号和用户备注极易被带入长期审计表。

## 7. 来源快照、文件与外部内容风险

### 7.1 SourceSnapshot 边界

来源快照用于可追溯，不是网页镜像服务。优先保存用户提供的链接和经脱敏的必要摘录；`content_hash` 用于发现静默变化，不能用于判断来源可信或用户资格。

- URL 仅允许 `https`（开发测试可特批）；拒绝 `file:`、`data:`、`javascript:`、内网 IP、localhost、link-local、私网和云元数据地址。
- 若产品只保存用户粘贴 URL，客户端链接应以新窗口打开，并避免在 URL 中拼接用户标识、活动状态或令牌。
- 若未来由服务器抓取，必须在独立低权限 worker 中进行：DNS 解析和连接时双重拦截私网地址，限制重定向次数，禁止向外带认证头，限制响应大小、超时、Content-Type 和下载速率。
- 来源正文按不可信内容处理：抽取纯文本或使用严格 sanitizer，不执行脚本、不渲染内嵌 iframe、不加载远程资源。规则 DSL 只能使用白名单结构化字段，禁止执行用户/来源文本。

### 7.2 P1 上传和导入

| 环节 | 必须控制 |
| --- | --- |
| 接收 | 身份验证、按用户配额、最大文件大小/页数/行数、速率限制、扩展名与文件魔数双重校验；拒绝压缩包、可执行文件、宏文档和不支持格式。 |
| 隔离 | 上传到私有 quarantine bucket；随机对象名；不允许 API/浏览器直接根据原文件名访问；落库前执行恶意内容扫描。 |
| 解析 | 隔离进程/容器、CPU/内存/时间限制、禁网、禁子进程；CSV/JSON 限制列数、嵌套层数和字符集；PDF 不执行 JavaScript/嵌入对象。 |
| 预览 | 仅呈现结构化候选值及错误，不自动写业务表；敏感列掩码；每条候选具有行号、来源文件哈希和 parser version。 |
| 确认 | 用户逐条或按明确批次确认；将每条写入转换为常规幂等命令；任一批次失败必须可报告、可重试且不能产生隐式半写入。 |
| 保留与删除 | 原文件默认短期保留，到期自动删除；用户删除账户或撤销导入时清理对象、派生预览和索引；保留哈希及最小审计记录。 |
| 导出 | CSV 单元格以安全文本导出，避免以 `=`, `+`, `-`, `@` 开头触发表格公式；JSON 不携带密码哈希、会话或对象存储 URL。 |

附件和导入文件绝不能作为公开静态资源目录的一部分。对象读取必须由应用重新授权后签发短时 URL，且需要记录访问审计。

## 8. P1 导入与 P2 同步

### 8.1 P1 导入的安全契约

导入的完整路径为：`上传/登记 -> 隔离 -> 扫描和解析 -> 候选预览 -> 用户确认 -> 幂等命令写入 -> 对账/审计 -> 原件到期清理`。任何步骤失败时，后续步骤不得执行。

- `SourceSnapshot(captured)` 与被确认的 `SpendEntry`/`PointsEntry` 分离；解析器不能直接写账本、活动报名或权益使用。
- 导入批次有所有者、状态、哈希、来源、parser version、创建/到期时间和撤销状态；行级结果只对批次所有者可见。
- 重复检测至少使用文件哈希和行指纹；发现相似行只提示确认，不能擅自覆盖手工记录。
- 用户撤销导入时，系统列出会受影响的已确认流水，并仅以显式反向/作废命令处理，保留审计链路。

### 8.2 P2 第三方同步的前提

第三方同步不是 P0/P1 的隐含能力。启用前需形成单独的威胁建模、供应商评估、授权界面、隐私告知、数据处理协议和事故响应方案，至少满足：

- 不收集银行用户名、密码、验证码或设备认证材料；只使用符合授权模型的 token/授权码。
- connector 独立于活动/积分等业务聚合，令牌使用 KMS 信封加密并与业务数据库列隔离；运行账号最小权限，令牌不进入 trace、队列或导出。
- 授权页清晰列出提供方、scope、读取范围、同步频率、保留期、末次同步和撤销入口；用户可随时撤销，并删除连接器原始数据和未来任务。
- 同步结果首先作为 `external_transaction` 待匹配事实进入队列，由用户确认后才产生刷卡任务/积分账本变化。connector 不可直接改写已确认历史。
- 同步游标、webhook 签名、重放窗口、失败重试、供应商不可用、部分数据与重复投递都须有隔离和审计策略。

## 9. 账户删除、备份与保留

### 9.1 删除语义

当前基线在删除申请后立即撤销会话并由 worker 清理现有表，再匿名化用户。工作台扩展前，应把下列对象加入“账户删除注册表”：卡活动及报名、权益及使用记录、积分账户/批次/账本、兑换、来源快照、导入批次和文件、对象存储副本、连接器令牌和游标、读模型、搜索索引、缓存、通知任务以及审计记录。

- 删除申请需明确说明：立即停止访问、是否存在冷静期、撤销方式、业务数据清理时点、审计匿名化方式和备份自然过期时间。
- 导出和删除属于高影响操作。除当前会话与限流外，P0 发布前应使用近期登录/密码确认或等效再认证，并在 UI 显示不可恢复风险；删除动作应允许在冷静期内取消，若不提供冷静期必须在确认页明确说明立即进入清理队列。
- 删除 job 必须幂等、可重试、有分对象完成状态且不泄露失败中的业务内容。无法清理对象存储或连接器数据时应告警并保留最小错误代码。

### 9.2 备份与恢复

- 生产数据库、对象存储和备份均应加密；备份密钥与数据库/对象存储凭据分离，访问按最小权限并记录审计。
- 建立书面保留表：在线业务数据、审计、导入原件、附件、日志、数据库备份和对象存储版本各自的最长期限、销毁任务和例外审批。不能把“备份自然过期”留为未定结论。
- 恢复演练在隔离环境进行，恢复后的数据不得用于开发或截图；演练记录 RPO/RTO、权限验证和删除请求在恢复副本上的处置。
- 用户删除后，在线系统需先不可访问；备份中的残留按已披露的最长期限过期，不为常规查询重新恢复已删除账户数据。

## 10. 分阶段安全门槛

### 10.1 P0：手工工作台发布门槛

| 类别 | 必须满足 | 验收证据 |
| --- | --- | --- |
| 数据边界 | 服务端拒绝完整卡号、CVV、密码、token、验证码和客户端 `owner_user_id`；只保存后四位及最小化手工数据。 | API 负向测试、日志/导出敏感扫描、字段审查。 |
| 鉴权 | 每个新 API 和后台命令从会话取得用户，按 `(id, user_id)` 验证主体与全部关联 ID；跨用户读取/写入/下载均返回 `404`。 | API contract tests 覆盖活动、权益、任务、积分、兑换、来源。 |
| 状态完整性 | 活动报名、权益使用、任务记录、积分调整、兑换均有状态机、版本/来源引用、审计和幂等命令；积分余额只能由账本投影得到。 | 并发、重放、乱序、reversal、规则变更单元与 PostgreSQL 集成测试。 |
| 规则可信度 | 规则、来源和用户记录明确区分；未确认或过期规则不自动给出资格/收益结论。 | UI/E2E 断言与领域测试。 |
| 会话与 Web 防护 | 保持现有 Origin 校验、安全响应头、会话 Cookie、生产 HTTPS 配置和敏感操作限流；所有新 API 在 middleware 覆盖范围。 | 生产配置 smoke test、Origin/CSRF 测试、headers test。 |
| 导出/删除 | 导出和删除经再确认/近期登录、审计、限流；删除注册表覆盖所有 P0 新表与后台任务，无法清理可观测。 | 端到端测试、删除 job 重试测试、导出内容审查。 |
| 生产运维 | 数据库 TLS、最小权限运行账户、secret 注入、分布式或平台级限流、备份加密及至少一次恢复演练。 | 部署清单、恢复演练记录、权限/网络配置审查。 |

P0 明确不包含：附件上传、CSV/PDF 解析、服务器抓取任意来源网页、第三方银行同步、保存银行登录材料、自动兑换或自动判断银行资格。

### 10.2 P1：附件与导入发布门槛

在满足 P0 后，以下所有事项必须完成才可开放给真实用户：

- 私有对象存储、隔离区、恶意文件扫描、短时下载授权、访问审计、内容类型/尺寸/页数/行数限制和到期清理。
- 导入 preview/confirm、解析沙箱、文件/行去重、原始文件哈希、parser version、事务化确认及可逆的导入撤销。
- 来源快照 URL/内容防 SSRF 与 XSS；不可信 HTML/PDF 不直接同源预览或执行。
- 针对压缩炸弹、恶意 CSV、公式注入、超大 PDF、重复上传、跨用户批次访问和删除后残留文件的自动化测试。
- 更新隐私说明、保留期限和用户可见的附件/导入删除入口。

### 10.3 P2：第三方同步发布门槛

P2 需要独立签收，不得因 P1 已完成而自动开放：供应商安全/合规评估、OAuth/connector 威胁模型、最小 scope、token KMS 管理、撤销/删除、webhook 签名和重放防护、同步隔离/确认队列、异常监控、事故响应演练以及灰度与一键关闭开关。

## 11. 必测安全场景

以下测试应进入工作台实现的自动化验收，而不是依赖人工走查：

1. 用户 A 枚举或提交用户 B 的卡片、积分账户、活动、规则、来源、兑换、导入批次和附件 ID，均不能读取、写入或推断存在性。
2. 同一兑换请求在网络重试、双标签页、队列重复和服务超时后最多形成一次 reservation/扣减；同键异 payload 得到 `409`。
3. 积分余额不足、批次过期、账户冻结、退款和 reversal 不会产生负余额或删除历史账本。
4. 活动报名/权益核销的非法状态跳转、规则版本不匹配、卡片已归档、时间窗不一致和篡改证据等级均被拒绝或转为待核对。
5. 手工任务累计、修正与撤销重放后，重算值、审计链路和 UI 证据等级一致。
6. 日志、错误、审计、队列和导出中不出现完整卡号、CVV、密码、Cookie、token、原始来源用户参数或未脱敏附件 URL。
7. 伪造 Origin、缺少生产 `APP_URL`、过期/撤销会话、CSRF 写入和超限登录/导出/删除均按预期拒绝。
8. CSV 公式、超大/畸形文件、伪造 MIME、PDF 嵌入内容、恶意 SVG、重复文件/行和解析超时不导致写账、XSS、SSRF 或资源耗尽。
9. 用户删除后，当前表、对象存储、缓存/任务、连接器 token 和导出链接不可访问；备份保留状态可由运维记录证明。
10. 备份恢复到隔离环境后，数据库权限、加密、行级/服务层隔离和删除处理均得到验证。

## 12. 未决问题与需签收决策

1. **P0 再认证方式**：导出、删除、兑换确认、授权撤销究竟使用密码确认、近期登录窗口还是 WebAuthn 等机制，需要产品和架构确定统一体验。
2. **附件是否进入 P1**：PRD 已列为 P1，但应确定允许格式、最大大小、默认保留天数、扫描供应商及是否允许用户下载原件。
3. **来源抓取策略**：P0 建议仅登记 URL/手工摘要；若要服务器抓取，需要明确允许域名、隔离运行时和内容保留策略。
4. **积分 reservation 语义**：用户记录“已提交兑换”时是否立即预留积分、何时扣减、预留多久自动释放、退款如何分配批次，需要产品/DBA 一致定义。
5. **删除与备份期限**：当前文档有建议但没有部署层已承诺的 RPO/RTO、备份和附件保留期限；在向用户承诺删除前必须由运营/合规签收。
6. **RLS 启用时机**：应用层所有权过滤是现状，生产工作台应在扩展迁移前决定是否以 PostgreSQL RLS 作为纵深防护，并验证 worker 的受控旁路。
7. **分布式限流与异常检测**：单实例内存限流不能作为多副本公网部署的最终控制；部署方案需要选定平台 WAF/网关或共享存储实现。

## 13. 交付边界与验证

本评审只新增本安全文档，不修改业务代码、迁移、PRD、架构、UX 文档或协作台账。文档中的“当前已实现”依据现有代码与文档静态审阅；“必须控制”均需在对应功能实现时以代码、迁移、自动化测试、部署配置或运维演练重新验证。

建议集成时将本文件的 P0/P1/P2 门槛映射到架构阶段和 QA 验收矩阵，并在每个阶段记录测试报告、迁移审查、渗透/负向测试结论和未接受风险。
