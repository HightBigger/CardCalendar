## 1. 结论

产品方向成立，但“优先级合理”必须解释为用户价值排序，而不是把所有字段都承诺在同一版本。最有价值且可交付的首条纵切是：**建卡 -> 保存来源/规则 -> 按卡参与活动 -> 单卡刷卡任务 -> 预计/确定进度 -> 用户确认奖励结果 -> 站内提醒**。这条 P0 旅程闭环后，用户能回答“我是否需要行动、还差多少、证据是什么、结果有没有到账”，同时不会被误导为银行已认定。

P1 应继续拆成两个独立发布门：P1-a 权益下发/预约/核销，P1-b 积分账户/批次/外部兑换记录。P1-b 的价值高，但账本、批次差额和兑换退分的可重放要求明显高于普通表单；没有数据库事实源和重放测试时，不应只发布一个“积分中心”外壳。P2 自动化和导入均应延后。

公开规则只作为字段维度的例证：例如中国银行年费页面体现产品和消费排除项差异，招商银行公开积分规则体现入账后生效、退款扣回和交易/活动奖励分离，中国银行历史贵宾厅规则体现凭证下发、现场核验和服务商限制，建设银行积分商城帮助页体现订单、配送、售后和积分规则是不同履约维度。它们不能转化为跨银行默认金额、比例、期限、资格或库存。

## 2. 优先级复核

| 范围 | 用户价值 | 可交付性判断 | 产品决定 |
| --- | --- | --- | --- |
| P0 活动/刷卡任务/奖励核对 | 直接降低错过截止日和错误刷卡风险，是主画像最高频任务 | 可交付，但前提是只保留确定的规则口径、单卡任务、手工事实和站内提醒 | 保留；把复杂表达式、多奖励编排和自动导入排除出 P0 |
| P1-a 权益 | 让高端卡用户知道“凭证是否下发、预约是否成功、是否真正核销” | 可交付为手工记录；保险理赔、年费减免和服务商索赔不是同一额度模型 | 保留基础 consumable/service 纵切；其余功能延后 |
| P1-b 积分账户/批次/兑换 | 解决多账户、到期和兑换结果不可追溯问题 | 高风险；需要 append-only ledger、lot 差额、负余额和双状态订单 | 保留为独立 feature flag；先过账本重放和兑换幂等门再开放 |
| P2 导入/同步/自动化 | 可减少录入成本，但会扩大隐私、误判和授权面 | 当前年费 MVP 无法支撑；需要安全、合规、恢复和供应商评审 | 明确延后，不作为“已规划可用”描述 |

## 3. 必须合并的修订（最多 10 项）

以下修订按产品风险排序，均应合并到正式 PRD/发布门；本文不直接修改那些文件。

1. **冻结 P0 的最小可成功路径。** P0 验收以“一个用户、一张卡、一个有来源的活动、一个单卡任务、一个奖励组件”为最小夹具；多卡规则仍支持，但多卡隔离是扩展验收，不要求用户首次建档一次填完所有卡。没有来源时允许保存为“线索/待核对”，但不能创建可执行的确定达标承诺。

2. **把 P0 任务表达式裁剪为有限集合。** `count`、`amount`、`count_and_amount`、`count_or_amount` 可执行；`custom` 在 P0 只能保存原文并显示待核对，不能进入自动进度计算。否则验收无法判断解析语义，交付会退化为自由文本。

3. **将活动实例与规则身份强制分开。** 周期或重复活动必须使用 `activity_instance_key`，每张卡独立 participation、SpendTask 和 ActivityReward；活动级列表只能展示聚合计数。跨卡消费、跨持有人或附属卡是否计入，未知时显示阻断原因，绝不隐式合并。

4. **统一 canonical 状态和兼容读映射。** 新写入只使用对齐稿定义的资格、报名、名额、进度、奖励、权益预约/核销、订单履约/积分扣减状态。`unchecked/eligible/uncertain/pending/fulfilled/debited/returned` 等旧词只能在兼容读取层映射，并在产品文案中给出明确中文含义；不得让同一状态在不同页面表示不同事实。

5. **让未知状态可行动而非只显示标签。** 所有 `unknown/needs_review/disputed` 必须携带 `reason_code`、`evidence_note`、`last_verified_at` 和 `next_action`（打开官方来源、补报名结果、核对入账、确认到账等）。缺少这些字段时，详情页可以保存但不得生成最终达标、可用、到账、到期提醒或收益结论。

6. **补齐 P0 提醒的用户闭环。** 活动截止、任务截止、奖励核对三类提醒采用稳定 dedupe key、用户 IANA 时区和对象深链；提醒状态支持稍后处理、完成、忽略和恢复。没有规则给出的奖励期限时，只允许用户手动设置核对节点，不生成“逾期奖励”。归档卡或取消任务停止未来提醒但保留历史。

7. **将 P1-a 权益按使用模型收窄。** 首个 P1-a 只交付 `consumable_quota` 与 `service_eligibility`：下发 -> 预约 -> 出示 -> 核销/拒绝/争议，只有首次 `redeemed` 扣减额度。`coverage_claim`、`fee_credit`、保险理赔、年费减免/返还和服务商索赔改为 P2 或独立 feature flag，不能共用“剩余次数”。

8. **把 P1-b 账本和兑换拆成可验证的发布门。** 积分页必须并列显示 `confirmed_balance`、`ledger_balance`、`lots_remaining_total`、`reconciliation_difference`、`unallocated_difference` 和各自 as-of；任一差额不为零或未知即 `mismatch/needs_review`。兑换订单状态与积分扣减状态分开；只有用户确认官方扣分才写幂等 debit，只有存在 posted debit 且用户确认退回才写 reversal。余额为负时保留真实负数并提示核对，不截断为零。

9. **为“快照/流水”与“外部结果”写出可测试的输入契约。** SpendTask 的 `snapshot` 与 `entries` 二选一，不能双算；`occurred/posted/settled` 口径要在任务激活时冻结。所有新增/反向流水使用业务幂等键，同 key 同参数重放原响应，同 key 异参数返回 409；退款保留原事实并追加关联负向记录，跨周期退款把当前结论转为 `needs_review`，不删除历史确认。

10. **把产品验收改写成 Given/When/Then 证据。** 每条验收必须注明发布门（P0/P1-a/P1-b）、前置数据、命令或 UI 操作、预期状态/数值、审计或数据库证据和错误码。至少补齐：空来源建档、资格未知、报名已提交未确认、名额未知、截止日跨时区、重复提交、跨用户/跨卡引用、权益并发核销、订单成功但扣分 pending、失败退分未知和负余额。仅写“页面不能显示”不足以执行验收。

## 4. 核心用户旅程复核

### P0：活动与刷卡任务

旅程在产品价值上闭环，但必须把两个分支写进验收：

- **来源不可用分支**：用户可先保存活动标题、适用卡和“线索待官方核对”，随后从详情补来源；在补齐前可提醒“核对来源”，不能显示可执行刷卡目标。
- **奖励未确认分支**：任务达到本地目标后进入“达标，待奖励核对”；奖励期限未知时停在待核对，期限明确且逾期才进入 delayed。奖励到账、撤回、争议均保留时间线。

活动、报名、名额、任务和奖励五轴独立，能避免把“提交报名”或“消费达标”误报成银行成功。活动级聚合只用于导航，不是可写的总状态。

### P1-a：权益

基础使用旅程闭环为“录入规则 -> 凭证下发 -> 外部预约 -> 出示 -> 核销/拒绝/争议 -> 重算额度”。预约成功不是使用成功；拒绝、取消和争议不扣减。保险理赔、费用减免和服务索赔缺少共同的可重算额度事实，应明确不在基础 P1-a。

### P1-b：积分与兑换

“官方余额观察 -> 有证据批次 -> 外部兑换 -> 订单结果 -> 用户确认扣分 ->（如有）用户确认退分”是闭环。没有批次证据时仍可记录总余额，但只能显示未分配差额和到期未知；订单成功但扣分未知、失败但退分未知都必须停在处理中/待核对。产品需要允许用户在兑换后回到同一订单补证据，否则双状态设计无法完成实际对账。

## 5. 未知/待核对状态审查

现有状态集合覆盖主要风险，且正确区分 `unknown` 与 `not_applicable`。仍需补三项产品约束：

1. `unknown` 不能作为空值的视觉别名；必须显示缺失事实、影响范围和下一步。
2. `needs_review` 与 `disputed` 要区分：前者是证据不足或规则过期，后者是用户记录与外部结果冲突；两者都不能进入最终成功。
3. `expired`、`cancelled`、`rejected` 是已知结果，不应被统一折叠为未知；历史对象可查看，但不能产生新的行动提醒。

建议详情页固定显示：状态、阻断原因、来源/证据、最后核对时间、下一步动作。这样未知状态才真正帮助用户作决定，而不是增加状态噪音。

## 6. 验收可执行性复核

现有 20 条产品验收方向正确，足以覆盖主要不变量，但还存在三类执行缺口：

- **术语缺口**：部分章节仍混用 `pending` 与 `expected_pending`、`fulfilled` 与 `success`、`redeem` 与 `redeem_debit`。必须先完成第 3 项修订，否则自动化测试会出现同义分支。
- **证据缺口**：验收常写“不能显示”“可重放”，未明确是 API 响应、读模型、审计时间线还是数据库重放结果。按第 10 项补证据类型和错误码。
- **发布门缺口**：P1-a 和 P1-b 的验收不能随 P0 一起标为“首版通过”；每个门都要有 feature flag、迁移/回滚证据和最小端到端旅程。

## 7. 明确延后项

以下项目不影响 P0/P1 手工闭环，应从首版承诺、默认入口和验收中移除，直到有独立授权与安全/合规/恢复评审：

- 银行登录、OAuth/账单连接器、短信/邮箱读取、自动同步和 webhook。
- PDF/OCR/CSV/JSON 直接写入 SpendEntry 或 PointsEntry；P1 仅可做只读预览，逐行确认写入放 P2。
- 系统内积分 `hold/reservation/release`、自动 FIFO/lot 分配、跨账户积分 transfer 和部分退款。
- 自动报名、抢名额、预约权益、兑换商品/里程、支付或联系客服。
- 保险理赔、年费减免/返还自动核算、服务商索赔和外部履约连接器。
- 邮件/Push、多设备离线同步、附件上传与长期保存；P1 先用备注和掩码引用。
- 规则模板自动填数、重复活动检测、规则差异订阅和批量编辑。
- 个性化“最优刷卡”、收益预测、办卡/销卡建议；价值记录只做用户确认的回顾算术。

## Decisions

- 保留 P0 活动/单卡任务/奖励核对作为最高用户价值纵切，但裁剪 P0 `custom` 表达式和复杂自动化。
- 将 P1-a 权益限制为可重算的下发、预约、核销事实；将 P1-b 账本与兑换作为独立发布门。
- 采用五轴活动状态、权益预约/核销双轴、订单履约/积分扣减双轴；旧状态只兼容读取。
- `unknown`、`needs_review`、`disputed` 必须有原因、证据时间和下一步；未知不触发成功、可用、到账、到期或收益结论。
- 所有验收改为带夹具、操作、预期状态和证据位置的可执行测试；银行公开规则只作建模例证，不作默认值。

## Risks/open questions

- 正式 PRD、架构、DB、QA、UX 仍存在少量 canonical 状态和提醒 DDL 漂移；在 Gate 0 冻结前不能进入实现。
- P1-b 的 lot 分配、对账差额和订单乱序处理需要影子 PostgreSQL、重放和恢复证据；产品文档不能替代这些验证。
- 银行活动的资格、名额、支付路由、MCC 排除、发奖/退分时点和权益服务商限制按具体规则变化，必须逐条保存来源版本和用户核对证据。
- “用户确认最终结果”是否必填、以及奖励核对节点的默认提醒日期，需由最终 UX/API 契约确定；规则未给期限时不得自动推断。
- 附属卡计入、合并积分池与多币种金额的业务口径仍须用户按官方条款确认，不能用跨银行模板补全。
