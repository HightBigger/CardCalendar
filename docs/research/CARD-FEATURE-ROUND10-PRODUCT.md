## 1. 本轮结论

第九轮已经冻结了五条独立记录链、规则版本、`unknown/needs_review/disputed` 和“来源不等于个人资格”的原则。本轮不再增加一套状态机，增量集中在一个问题：**状态是否能告诉用户下一步做什么，以及这个结论何时需要重新核对**。

用户最终要完成的是一组外部行动，而不是把页面上的状态改成“完成”：

```text
活动：发现 -> 预检 -> 外部报名 -> 达标核对 -> 奖励逐项核对
权益：确认下发 -> 预约 -> 出示/使用 -> 拒绝或争议处理
刷卡：选择路由 -> 等待入账/清算 -> 解释计入 -> 退款/冲正重算
积分：观察快照 -> 分辨批次/到期 -> 对账 -> 兑换预检 -> 履约/扣分/退分
```

本轮必须补齐的产品契约有五项：

1. 在报名、激活任务、记录兑换等关键动作前重新检查来源新鲜度；过期或不完整的规则只能阻断承诺，不能阻断用户保存线索。
2. 把“待核对”变成带原因、复核日期和深链的行动项，并提供可解释的排序；排序是工作台提醒，不是金融建议。
3. 规定一笔消费如何被多个活动/任务引用。只能保留一个原始消费事实，各任务各自评估，不能复制金额造成双算。
4. 明确报名重试、活动取消、跨周期退款、凭证轮换、部分履约和退分等待等可恢复边界。
5. 统一用户文案：官方规则证明的是规则维度，不证明个人资格、名额、实时余额、库存、发奖或退分。

## 4. 与现有 PRD 的差距清单

### 4.1 缺失：需要新增的产品契约

| 编号 | 缺口 | 对用户的影响 | 建议归属 |
| --- | --- | --- | --- |
| M-01 | 没有统一“规则新鲜度/复核租约”动作点。`last_verified_on` 有字段，但报名、任务激活、兑换提交何时必须重核未定义。 | 用户可能依据已失效规则继续消费或兑换。 | P0：规则有效期、新鲜度阈值和三处动作前复核。 |
| M-02 | 待核对事项没有统一排序和可执行队列。 | 截止日、资格未知、奖励延迟同时出现时，用户不知道先处理什么。 | P0：按截止风险、阻断程度、证据新鲜度排序；允许用户改优先级，不生成价值建议。 |
| M-03 | 报名没有尝试历史/重试/撤销语义。 | 重复提交可能被误记为两次成功，失败后无法解释是否还能重试。 | P0：attempt 序号、幂等键、失败原因、重试前置条件。 |
| M-04 | 一笔原始消费跨多个任务的归属规则未写入产品契约。 | 用户为两个活动复制录入金额，进度和审计会双算。 | P0：canonical spend fact + per-task evaluation；禁止复制原始金额。 |
| M-05 | 活动取消、规则撤回与未结束任务的动作没有统一文案和状态顺序。 | 用户可能在活动已取消后继续刷卡。 | P0：停止未来提醒/新消费，保留历史，奖励状态转待核对。 |
| M-06 | 奖励核对没有“应核对窗口”和争议下一步。 | 用户知道奖励迟到，却不知道何时再查、应找银行还是合作方。 | P0：只有有官方期限才计算 expected_on；否则只给手动复核节点。 |
| M-07 | 权益获取阶段缺少激活/凭证轮换的可恢复路径。 | 页面可能把“卡片含权益”误显示为“当前可用”。 | P1-a：delivery/activation/credential 的下一步和证据。 |
| M-08 | 权益候补、预约过期、服务商变更没有占用/恢复说明。 | 预约取消可能被误扣次数，或候补成功后无法记录新凭证。 | P1-a：reservation timeline，不写 consume。 |
| M-09 | 积分快照新鲜度和对账修复流程未产品化。 | 用户看到旧余额，却无法判断先补快照还是补流水。 | P1-b：`as_of`、freshness、三种补证动作、负余额提示。 |
| M-10 | 兑换的 item/组件级部分履约、现金部分和合作方拒绝尚未形成最小用户流程。 | 一单两件只成功一件时，整单“完成/失败”会误导扣分和退分。 | P1-b：item 级结果；订单、履约、debit、refund 四轴继续独立。 |
| M-11 | “规则证据”和“个人事实”的显示文案没有集中契约。 | 用户可能把“官方页面已读取”理解为“我有资格”。 | P0 横切：固定文案与状态标签见第 5 节。 |
| M-12 | 同一对象在多张卡/多周期的提醒和价值回顾没有明确去重边界。 | 用户收到重复提醒，或跨卡价值被错误合并。 | P0：提醒按 participation/instance；价值按卡和期间汇总，跨卡只做可见分组。 |

### 4.2 重复：已有契约，应保留但不再新增同义字段

| 已有内容 | 处理 |
| --- | --- |
| 资格、报名、名额、任务进度、奖励到账五条独立事实 | 保留；本轮只补动作闸门和文案，不再增加“活动总状态”。 |
| `snapshot/entries` 二选一、occurred/posted/settled、预计/确定进度 | 保留；本轮补跨任务引用和跨周期退款的用户解释。 |
| 权益下发/预约/出示/核销/拒绝/争议、只有核销扣次数 | 保留；本轮补候补、凭证轮换和恢复动作。 |
| confirmed/ledger/lots、两个有符号差额、未知批次不提醒 | 保留；本轮补新鲜度和对账操作顺序。 |
| 订单/履约/debit/refund 四轴、失败不自动退分 | 保留；本轮补 item 级部分履约。 |
| Source/RuleVersion、访问日期、适用期、`unknown` | 保留；本轮补重核时机和用户可读解释。 |

### 4.3 冲突或容易误解：需要整合时先决策

| 冲突 | 风险 | 第十轮决策 |
| --- | --- | --- |
| `CardActivity.applicable_card_ids` 可关联多卡，但 P0 纵切是单卡单周期。 | UI 可能把多卡合计成一个达标值。 | 多卡只表示规则适用范围；写入和提醒必须按 participation `(user, campaign, card, instance)` 隔离。 |
| 兼容投影允许 `CardActivity.reward_status=pending`，规范奖励使用 `expected_pending`。 | 新写入出现两个“待发”含义，读模型难解释。 | 只读兼容映射；新写入和验收只认 canonical 组件状态。 |
| PRD 将 P1 权益、积分和兑换写在同一节，但 Round9 已分 P1-a/P1-b。 | 一个模块未完成却阻塞或误宣称整个 P1。 | 发布门拆成 P1-a、P1-b，各自 feature flag 和验收。 |
| `SpendEntry.task_id` 的单任务形态与“一笔消费可能满足多个活动”用户事实冲突。 | 复制流水会双算，拒绝复用又迫使用户重复录入。 | 由架构/DBA 选择 canonical spend fact + link/evaluation；在决策冻结前禁止跨任务自动复制。 |
| 兑换“计划”与“可兑换”容易混用。 | 规则/库存未知时提前给出购买承诺。 | UI 只用“兑换计划/待核对”；“预检通过”也需附官方页面最终确认。 |

## 5. 用户可解释文案契约

所有状态标签同时显示：原因、证据日期、影响、下一步。以下文案可直接作为产品基线，禁止用“实时”“保证”“已成功”替代未知状态。

| 场景 | 推荐文案 | 不应出现 |
| --- | --- | --- |
| 规则页面已读取 | “官方规则已读取（访问于 YYYY-MM-DD）；这只说明来源正文可访问，不代表你符合资格。” | “你已符合”“已自动验证” |

## 6. 优先级与首个可开发纵切

### 6.1 发布建议

| 优先级 | 交付内容 | 依赖与验收门 | 明确不承诺 |
| --- | --- | --- | --- |
| P0 | 活动发现/预检/报名记录、单卡单周期 SpendTask、冻结支付路由、预计/确定进度、跨任务引用策略、退款重算、奖励组件核对、待核对行动队列和固定文案。 | Gate 0 冻结 canonical 状态、来源新鲜度、提醒去重、ownership、幂等和跨任务 link；Gate 1 通过手工纵切、回放和跨时区验收。 | 银行登录/同步、自动报名、自动资格判断、自动发奖、库存同步、最优刷卡建议。 |
| P1-a | 次数型/服务资格权益：下发/激活、预约/候补/改期、出示、首次核销、拒绝/争议、凭证轮换和周期实例。 | 单独 feature flag；通过额度账本、重复核销、预约取消、凭证失效和恢复测试。 | 保险理赔自动化、费用抵扣自动核算、代预约、服务商连接器。 |
| P1-b | 积分余额快照、批次/到期、双差额对账、兑换预检、item 级履约、debit/refund 四轴。 | 单独 feature flag；通过负余额、未知批次、用途限制、部分履约、退分幂等和恢复测试。 | 实时余额、自动 FIFO、系统 hold、库存锁定、自动下单/退分、跨账户转移。 |
| P2 | 授权后的隔离导入预览、规则差异订阅、只读连接器、外部通知和重复活动检测。 | 另做隐私、合规、误判率和供应商评审；导入不得绕过人工确认。 | 读取银行密码/短信、替用户报名/预约/兑换/支付、自动决定个人资格。 |

### 6.2 首个可开发纵切

最小夹具固定为：一个用户、一张卡、一个有官方来源的活动、一个 participation、一个 SpendTask、一个 canonical SpendEntry、一个奖励组件和一个站内提醒。

用户可以：保存来源 -> 完成预检或看到缺失项 -> 记录外部报名和回执 -> 激活冻结了路由/截止口径的任务 -> 录入消费并看到预计/确定进度 -> 记录退款反向事实 -> 独立核对奖励 -> 处理或忽略待核对项。

首个纵切不开放权益、积分批次和兑换写入口；这些入口在 P1-a/P1-b 通过各自发布门后再打开。若架构尚未实现跨任务 link，P0 必须明确禁止将同一 SpendEntry 复制到第二任务，而不是静默复制。

## 7. Given / When / Then 验收条件

### P0 活动、任务与提醒

1. **来源缺失阻止承诺**
   Given 活动只有第三方摘要且没有活动期；When 用户保存；Then 记录为线索/`needs_review`，显示缺失项和“补充官方来源”动作，不创建确定 SpendTask、奖励金额或“可参加”结论。

2. **关键动作前重新核对**
   Given 规则的最后核对日期超过用户设置的新鲜度阈值；When 用户点击报名或激活任务；Then 系统要求重新打开来源并确认，或保存为计划但阻止确定进度；审计记录旧/新核对时间。

3. **报名重复提交幂等**
   Given同一 participation 已有 `submitted` 尝试和掩码回执；When 用户再次提交相同请求；Then 返回原尝试，不新增报名事实；相同幂等键同参数重放结果一致。

4. **报名重试保留历史**
   Given 第一次报名被外部渠道拒绝且允许重试；When 用户记录第二次提交；Then 创建新的 attempt 序号，保留第一次原因和时间，不把 `submitted` 直接覆盖为 `confirmed`。

5. **报名失败停止刷卡提醒**
   Given 活动报名拒绝、名额未分配或已截止；When 保存结果；Then 未结束任务转为阻断/待核对，停止“继续刷卡”提醒，历史消费和报名证据仍可查看。

6. **多卡多周期隔离**
   Given 同一规则适用于两张卡或两个周期；When 分别录入消费；Then participation、任务、奖励和提醒分别计算，任何一张卡的金额都不进入另一张卡的确定进度。

7. **一笔消费不重复计数**
   Given 一笔 canonical SpendEntry 被两个活动引用；When 两个任务重算；Then 原始金额只保存一次，每个任务有独立 qualification 结果，汇总值不因复制流水增加。

8. **支付路由未知先保存计划**
   Given 任务只接受实体 POS，用户选择的路由为 `unknown`；When 激活；Then 可以保存计划和核对动作，但不能写入确定进度或显示“开始刷卡可达标”。

9. **入账口径和时区可解释**
   Given 用户时区为 `Asia/Shanghai`，消费发生在 UTC 跨日边界且任务要求 `posted`；When 重算；Then 使用冻结的用户时区和 `cutoff_basis`，显示原始时间、本地日期和待入账原因，不能按服务器时区静默归属。

10. **待入账不提前失败**
    Given 截止日已过但有一笔可能符合的 `occurred_only` 记录；When 查看任务；Then 显示“预计可能达标/等待入账”，不自动标记最终失败；用户可在入账后重新核对。

11. **退款追加反向事实**
    Given 已暂时达标的任务发生部分退款；When 录入退款；Then 原消费保留，新增关联反向 SpendEntry，受影响任务/奖励转 `needs_review` 或短缺，不能自动写退分。

12. **活动取消保留复盘**
    Given 活动已存在消费和部分奖励组件；When 用户记录官方取消；Then 停止未来消费/奖励提醒，历史 participation、任务、流水和奖励仍只读可见，不自动标记到账。

13. **奖励期限不被猜测**
    Given 来源没有发奖期限；When 任务被用户核对为达标；Then 奖励组件保持待核对并允许用户设置复核节点，不生成系统逾期结论；有明确期限时才按用户时区生成提醒。

14. **待核对事项可行动**
    Given 对象状态为 `unknown/needs_review/disputed`；When 保存；Then 必须有原因、证据时间、影响和 `next_action` 深链；用户选择忽略只停止提醒，不删除历史。

### P1-a 权益

15. **下发/凭证未知不显示可用**
    Given 卡片规则写有权益，但凭证尚未下发或已过期；When 打开权益；Then 显示“已记录权益，凭证/当前可用性待核对”，不增加可用次数，也不生成已使用价值。

16. **预约改期/取消不扣次数**
    Given 次数型权益剩余 2 次且预约已确认；When 用户取消或改期且未现场核销；Then 剩余次数仍为 2，预约时间线保留原记录和新状态，不写 `consume`。

17. **首次核销幂等**
    Given 同一权益使用的外部回执已记录 `redeemed`；When 用户重复保存相同回执；Then 返回首次结果，不新增扣减；不同回执需进入待核对而非自动扣第二次。

18. **现场拒绝不代表已用**
    Given 已预约并出示，但服务商因容量/地区拒绝；When 保存拒绝；Then 额度不变，记录服务商、地区、原因和外部争议动作，产品不判定责任。

### P1-b 积分与兑换

19. **余额快照显示新鲜度**
    Given 官方余额快照已有 90 天未更新；When 打开积分账户；Then 显示截至日期和“需更新官方余额”，不显示“实时/可用余额”，旧快照仍可追溯。

20. **未知批次不造到期**
    Given 账户有确认总额但没有可证明的 lot；When 查看到期和兑换；Then 显示未分配差额和补批次动作，不生成到期提醒、FIFO 扣减或可兑换结论。

21. **负余额原样保留**
    Given 退款扣回后 `ledger_balance=-20`；When 查看账户；Then 显示 -20 和对账动作，状态为 `mismatch/needs_review`，不得截断为 0 或自动创建补偿积分。

22. **兑换资格未知不写 debit**
    Given 兑换规则缺少适用卡/账户资格或库存/上限；When 用户保存；Then 只能保存为计划/待核对，不显示“可兑换”，不写入积分扣减流水。

23. **部分履约分轴**
    Given 一个订单两件商品只有一件履约成功且积分部分扣减；When 用户记录结果；Then item、订单、履约、debit、refund 分别保留，整单不能被标为完成，未履约部分有下一步。

24. **失败订单不自动退分**
    Given 履约失败且存在已入账 debit，但官方退分未确认；When 保存失败；Then `fulfillment_status=failed`、`refund_status=pending_external_confirmation`，不产生 reversal；补录官方退分证据后才追加一次幂等 reversal。

## 8. 产品风险与保持 unknown 的结论

| 风险 | 触发 | 产品控制 |
| --- | --- | --- |
| 规则失效 | 年度、卡种、地区或客群改变；动态页面替换正文。 | 规则快照不可变；关键动作前重核；历史任务继续引用旧版本。 |
| 资格误判 | 公开规则有邀请、白名单、资产或卡片状态条件。 | 资格默认 `unknown`；只有用户官方核对记录才能转为用户确认状态。 |
| 交易误判 | MCC、钱包路由、入账/清算日期和退款由银行最终认定。 | 冻结路由快照，预计/确定分离；排除必须带原因，不能仅凭商户名判断。 |
| 权益失效 | 凭证延迟、服务容量、服务商变更、现场拒绝。 | 下发/预约/核销分轴；拒绝不扣次数；保留投诉/核对动作。 |
| 余额不一致 | 用户快照、系统流水和批次来自不同时间。 | 显示两个差额和各自 `as_of`；未知批次、负余额不被修剪或自动分配。 |
| 兑换损失 | 商品不可取消、合作方异步到账、部分履约、退分延迟。 | 预检未知则计划化；四轴独立；失败不自动退分。 |
| 隐私暴露 | 回执、订单号、预约号和来源参数含敏感信息。 | 默认掩码，不收完整卡号/CVV/登录凭据/验证码；附件需单独安全评审。 |

以下结论必须保持 `unknown`，除非用户录入官方渠道证据并带访问时间：

- 用户个人是否符合活动/权益资格、报名是否确认、名额是否分配、服务现场是否可用。
- 某笔交易的最终 MCC、支付路由、发生/入账/清算日期及银行是否认定合格。
- 奖励具体发放日、库存、合作方到账时间、退分结果和争议责任。
- 实时积分余额、未知批次到期日、自动 FIFO 顺序、系统外扣分或退分是否发生。
- 兑换商品/里程当前资格、不可取消例外、部分履约责任和现金部分是否结算。
