## 1. 研究目标和方法

Round7 已冻结“活动参与实例与规则分离、资格/报名/名额/任务/奖励独立、支付路由快照、`snapshot/entries` 二选一、权益按 `usage_model`、积分双差额、兑换四轴”的基础契约。本轮不重新发明状态，而检查用户是否能在每个轴上完成下一步行动，并找出正式需求仍可能遗漏的边界：

1. 用户看到活动后，能否判断“先报名、先核资格，还是先补来源”，而不是直接被引导消费。
2. 用户能否知道某笔消费为何计入/待核对/排除，以及活动规则被修改后哪一个周期受影响。
3. 权益从下发、预约到核销的操作是否可恢复；预约、拒绝、服务商变更是否会错误扣减。
4. 积分批次、过期、待入账、负余额和兑换限制是否都有证据和下一步，而不是显示一个伪造的可用余额。
5. 订单履约、积分扣分、退分、现金部分和部分完成能否分别追踪。

研究步骤：

- 静态比对 PRD v0.8、Round7 产品稿中的用户任务、状态、发布门和 Given/When/Then，优先记录“用户决策缺口”而不是增加字段数量。
- 复查银行/卡组织公开官方页面，只提取页面明确出现的规则维度；页面不能证明 Cardfolio 用户的个人资格、当前库存、实时余额、发奖或退分结果。
- 对每个建议标记 P0/P1/P2、所需官方证据和应保持的 `unknown`；不能将历史页面的数值转成默认模板。
- 2026-08-15 使用 `curl -L --max-time 25 -s -o /dev/null -w '%{http_code} %{url_effective}' '<URL>'` 逐一检查来源可访问性；本次八个 URL 均返回 HTTP 200，正文仍可能动态变化，需在产品中保存访问日期和规则快照。

### 2.1 来源使用规则

- 来源记录必须包含 URL、标题、发布/生效信息（页面有则记录）、访问日期、来源等级、原文摘录和内容哈希；HTTP 200 不替代快照。
- 搜索摘要、第三方攻略和银行导航页只能作为 `lead`，不能激活确定的活动、任务、奖励金额、积分批次或权益额度。
- 历史规则可以支持“为什么需要这个字段/状态”的设计证据，但不可以填充当前模板值；规则过期或正文缺失时转为 `needs_review`。
- “官方来源已读取”只说明原文已被用户或系统读取，不代表官方为 Cardfolio 计算个人资格；最终资格、库存、余额、发奖和退分只能由用户在官方渠道确认并记录证据。

### 3.1 本轮建议的产品补充要求

**活动行动闸门（P0）**

1. 活动详情先展示“来源、适用卡/客群、活动期、报名截止、名额/配额、支付路由、奖励组件”七项预检。缺任何关键事实时允许保存线索，但操作按钮只能是“补充来源/核对官方”，不能是“开始刷卡”。
2. 报名记录要保留用户实际执行的外部动作和回执备注；重复提交必须提示可能重复报名，不能替用户再次报名。报名失败、名额未分配或活动已截止时保留复盘记录，并停止继续消费提醒。
3. 规则版本变更必须显示差异摘要和受影响的未结束实例。历史消费仍引用原版本；新消费必须明确选择新规则或创建新实例，禁止后台覆盖。
4. 奖励组件要有独立“核对入口”和截止/预计规则。只知道总奖励时保存原文，不把总额拆成可计算金额；组件已到账不代表其它组件成功。

**刷卡行动闸门（P0）**

5. SpendTask 激活前必须确认 `cutoff_basis`、路由快照和 `input_mode`。激活后修改这些值要创建新版本/新实例并保留旧任务的进度，而不是重算历史。
6. 每笔消费显示 `included`、`pending`、`excluded` 或 `disputed` 的原因，例如“尚未入账”“支付路由未知”“商户/MCC 在排除项”“币种不匹配”。用户可以补证据后重算，但不能直接把排除项改为计入。
7. 任务在截止日后仍有待入账记录时，显示“预计可能达标/等待入账”，而非最终达标；若发生退款，展示受影响奖励组件和需重新核对的周期。
8. 任务跨日计算必须以用户设置的 IANA 时区记录，页面同时显示本地日期和来源中的时间口径；不能使用服务器时区默默切换归属。

**权益行动闸门（P1-a）**

9. 次数型权益将“凭证可用、已预约、已出示、已核销、被拒/争议”作为时间线。预约改期/取消、凭证失效或服务商更换不写 consume；重复核销采用业务幂等键。
10. 权益周期重置要创建新的周期实例并保留上周期的实际使用；未知重置日只提示“核对周期”，不得按自然年自动补齐。
11. 现场拒绝必须记录服务商、地区、拒绝原因和用户下一步；产品不判定银行/服务商责任，也不自动恢复不存在的扣减。
12. 非次数型权益保存理赔、费用抵扣或服务完成等专属结果；估算价值和实际金额分开，估算不进入收益已实现汇总。

**积分和兑换行动闸门（P1-b）**

13. 账户详情并列显示 `confirmed_balance`、`ledger_balance`、`lots_remaining_total`、两个差额、各自 `as_of` 和来源新鲜度；任一未知或不一致都给出“补录官方余额/补批次/核对流水”的动作。
14. 待入账积分、已入账积分、过期、调整、兑换扣分和退分必须有不同流水类型；用户只知道总余额时不创建 lot，不自动推断 FIFO 或可兑换余额。
15. 兑换录入前显示规则证据、适用卡/账户、所需积分、现金部分、有效期、库存/上限和不可取消说明；任一未知则订单可保存为计划或待核对，但不能显示“可兑换”承诺。
16. 兑换的部分履约、合作方拒绝、订单取消、积分扣分成功但履约失败都保留原订单并分别更新四轴。失败不自动退分，退分必须关联已入账 debit 和外部证据。

**提醒、隐私和复盘（P0 横切）**

17. 每个待核对项必须有对象深链、`next_action`、用户时区下的复核日（如有）和稳定 dedupe key；用户选择忽略只停止提醒，不删除证据。
18. 来源摘录、订单号、预约号、凭证号和外部回执默认掩码；不允许记录完整卡号、CVV、银行登录凭据、短信验证码或支付密码。备注应支持删除/归档并保留审计事件。
19. 价值回顾只汇总用户确认的年费、实际权益金额和兑换结果；计划中、估算、待核对和争议金额独立标记，不生成收益保证或最优刷卡建议。

| P2 | 在授权后降低手工录入成本 | 隔离导入预览、重复活动检测、受控模板、外部通知和连接器的独立评审 | 读取银行登录、短信/邮箱、代用户报名/预约/兑换/支付、自动决定个人资格 |

### 4.1 指标补充

指标以用户主动录入/确认的数据为分母，不把银行的实时资格、库存、发奖或余额准确率作为 Cardfolio 可控结果：

- **行动闸门完成率（P0）**：保存活动后，在刷卡任务激活前完成来源、适用卡、活动期、支付路由和截止口径确认的比例，目标不低于 90%。
- **待核对可行动率（P0）**：进入 `unknown/needs_review/disputed` 后 14 日内完成下一步、延期或明确忽略的比例，目标不低于 60%。
- **排除原因可解释率（P0）**：被排除/待核对的 SpendEntry 中有结构化原因和证据时间的比例，目标不低于 95%。
- **权益事实完整率（P1-a）**：已记录权益使用同时具备凭证/预约/核销或拒绝结果的比例，目标不低于 80%。
- **兑换四轴完整率（P1-b）**：已记录兑换同时有履约、扣分、退分结果或明确未知原因的比例，目标不低于 80%。
- **历史不可变缺陷数**：规则改版、退款、取消、退分后历史事实被覆盖或静默删除的发布缺陷，目标为 0。

## 5. Given / When / Then 验收补充

以下 18 条是对 Round7 验收的增量，不替代 Round7 的 20 条。每条需要绑定发布门、API/UI 操作、错误码、读模型和审计/账本证据。

### P0 活动与刷卡任务

1. **来源预检阻止刷卡承诺**
   Given 只有第三方摘要且缺少活动期；When 用户保存活动；Then 保存为 `lead/needs_review`，显示“补充官方来源”，不创建确定 SpendTask、奖励金额或可参加结论；证据为来源等级、缺失原因和无任务事件。

2. **报名截止前后动作不同**
   Given 活动有 `enrollment_deadline`；When 当前时间在截止日前，详情显示报名动作；When 已超过截止日，不能新建报名提交，只能记录外部结果或复盘；证据为用户时区、规则版本和 409/业务校验结果。

3. **重复报名不重复提交**
   Given 同一 participation 已保存 `submitted` 和回执掩码；When 用户再次点击提交；Then 返回原记录或明确“已提交”提示，不创建第二个报名事实；证据为业务幂等键和事件数量。

4. **报名失败停止继续消费提醒**
   Given 报名被官方拒绝或名额未分配；When 保存结果；Then 未结束任务转为 `blocked/needs_review`，停止“继续刷卡”提醒但保留历史消费；证据为提醒 dedupe 状态和状态事件。

5. **规则版本变更不覆盖历史**
   Given 实例 A 已按规则版本 v1 录入消费；When v2 生效且门槛/排除项变化；Then A 仍引用 v1，新消费只能选择 v2 新实例或明确迁移动作；证据为两个 rule version、实例引用和重算结果。

6. **刷前支付路由未知**
   Given 任务只接受实体 POS，用户选择的支付路由为 unknown；When 激活任务；Then 允许保存计划但阻止“开始刷卡/确定进度”动作，并给出核对官方规则或交易凭证的下一步；证据为冻结快照和阻断原因。

7. **排除原因可解释**
   Given 一笔消费已发生但尚未入账，另一笔为指定钱包且规则排除；When 查看任务；Then 两笔分别显示 `pending` 和 `excluded` 及原因，不能只显示一个合计值；证据为 SpendEntry、method snapshot 和读模型。

8. **截止日与用户时区一致**
   Given 用户时区为 `Asia/Shanghai`，交易发生在 UTC 跨日边界；When 重算任务；Then 按任务冻结的用户时区和 `cutoff_basis` 归属，页面显示转换后的本地日期；证据为时区、原始时间和重算日志。

9. **活动取消保留历史**
   Given 活动已录入消费和部分奖励；When 官方来源确认活动取消；Then 停止未来提醒和新消费，历史参与/流水/奖励仍可查看，不能自动标记为已获奖或删除；证据为取消原因、事件时间线和提醒状态。

10. **退款影响奖励但不改写流水**
    Given任务已暂时达标且有积分奖励待核对；When 录入部分退款；Then 原消费保留，新增关联反向流水，任务和受影响奖励转为 `needs_review/shortfall`，不自动写退分；证据为 `reversal_of_entry_id`、重算值和奖励事件。

### P1-a 权益

11. **预约改期不扣次数**
    Given consumable quota 剩余 2 次；When 用户将已确认预约改期或取消但未核销；Then quota 仍为 2，预约时间线保留原记录和新状态；证据为 usage 事件且无 consume。

12. **凭证轮换需重新核对**
    Given 权益凭证已下发；When 用户记录凭证过期或服务商要求新凭证；Then `entitlement_status` 转为 `needs_review`，不增加或扣减额度，并生成补领/核对动作；证据为掩码凭证引用和原因。

13. **现场拒绝不代表已使用**
    Given 已预约并出示，但服务商因容量或地区拒绝；When 保存拒绝；Then 额度不变，记录服务商/地区/原因和争议动作；证据为 usage 状态、quota ledger 和审计。

### P1-b 积分与兑换

14. **待入账积分不进入已确认余额**
    Given 用户只有一笔待入账奖励和官方已确认余额；When 查看账户；Then 待入账单独显示，不改变 confirmed/ledger 差额，不能生成可兑换或到期结论；证据为 entry type、as-of 和读模型。

15. **负余额保留真实数值**
    Given 退款扣回后 ledger_balance 为 -20；When 打开积分账户；Then 显示 -20 和核对动作，账户为 `mismatch/needs_review`，不得截断为 0 或自动创建补偿积分；证据为反向流水和重放结果。

16. **兑换预检拦截未知资格**
    Given 兑换页面缺少适用卡/账户资格或库存上限；When 用户保存兑换；Then 可保存为计划/待核对，但不能显示“可兑换”或写入已扣分流水；证据为 rule source、资格状态和无 debit 事件。

17. **部分履约与扣分分离**
    Given 一个订单含两件商品，仅一件履约成功且积分已部分扣减；When 用户录入结果；Then订单、履约、扣分、退分四轴分别记录，不能把整单标成完成；证据为 item/组件事实、debit 金额和状态映射。

18. **失败订单不自动退分**
    Given 订单失败且存在已扣分记录，但官方退分尚未确认；When 保存失败；Then `fulfillment_status=failed`、`refund_status=pending_external_confirmation`，不生成 reversal；补录官方退分证据后才追加等额幂等 reversal；证据为订单事件、debit/reversal 关联和幂等响应。

## 7. 必须继续保持 unknown 的结论

以下结论即使来源页面可访问，也不能由 Cardfolio 自动推断，除非用户录入官方证据并记录访问时间：

- 用户本人是否满足活动资格、邀请/白名单条件、报名是否成功、名额是否分配。
- 某笔交易的最终 MCC、支付路由、发生/入账/清算日期及是否符合银行排除项。
- 规则没有明确给出的奖励比例、取整、发放日、税费、库存、合作方到账时间或退分结果。
- 权益当前是否仍可用、凭证是否下发、服务商/地区是否有容量、现场拒绝责任归属。
- 积分账户实时余额、未知批次的到期日、自动 FIFO 顺序、系统外扣分或退分是否已经发生。
- 兑换商品/里程的当前资格、库存、不可取消例外、部分履约责任和现金部分是否已结算。

这些 unknown 必须显示缺失事实、影响范围、来源/证据时间和下一步，不得生成“已达标、可用、已到账、可兑换、已过期或收益”的确定结论。
