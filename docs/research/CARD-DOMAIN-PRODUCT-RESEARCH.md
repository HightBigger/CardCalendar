| 项目 | 内容 |

| 文档状态 | 独立研究稿，供 PRD/架构/数据库合并评审 |
| 研究截止/访问日期 | 2026-08-14 |
| 研究角色 | 产品经理（Cardfolio） |
| 适用范围 | 中国大陆个人信用卡的活动、权益、刷卡方式/任务、积分账户与兑换记录 |
| 实现边界 | 只记录用户输入和用户从官方渠道核对的结果；不连接银行、不代报名、不代交易、不代兑换 |

## 1. 结论摘要

银行公开规则不能被压缩为一个“活动完成”或“积分到账”字段。至少要分开记录以下事实链：

```text
活动：发现 -> 资格核对 -> 报名 -> 名额/分配 -> 消费达标 -> 奖励待发 -> 到账/撤回/争议
权益：卡片适用 -> 凭证下发 -> 可用 -> 预约 -> 出示/现场核销 -> 已用/拒绝/争议
交易：发生 -> 待入账 -> 入账/清算 -> 纳入/排除 -> 退款/冲正
积分：确认余额 -> 批次及到期 -> 用户选择批次 -> 扣减 -> 退回/过期
兑换：计划 -> 提交 -> 处理中 -> 实物/票券/里程等履约 -> 成功/失败/退款/争议
```

本研究的产品决策：

1. **P0 先做活动和刷卡任务闭环。** 用户录入官方来源、活动资格/报名/名额、消费累计快照或手工流水，分别看到确定值和待入账值，最后手工核对奖励结果。
2. **P1 再做权益和积分账本。** 权益的下发、预约、现场核销分开；积分保留确认余额、流水余额、批次余额和未分配差额；兑换履约和积分扣减分开。
3. **规则数字不跨银行泛化。** 笔数、金额、积分比例、取整、有效期、渠道、MCC 排除和发放时点必须绑定卡种、活动、地区、时间窗及规则版本。
4. **未知值是产品状态，不是空白。** 资格、报名、名额、入账口径、奖励日、权益凭证、积分有效期、兑换退分等未核实时必须显示“待核对/未知”，不能用默认值推断。
5. **所有外部动作由用户在银行或服务商官方渠道完成。** Cardfolio 只提供待办、原文链接、记录入口、算术汇总和历史追溯。

### 2.1 来源使用原则

- 原文、标题、发布日（如有）、访问日、URL、适用卡/地区、有效期、原文摘录和来源等级必须随规则版本保存。
- 搜索摘要、第三方信用卡攻略和成熟产品页面只能记为“线索待官方核对”，不能直接创建可执行达标任务或填入奖励数值。
- 历史官方页面仍可用于设计状态（例如凭证下发、现场签名、退款扣回），但必须标注历史适用期，不能显示为当前权益。
- 动态或需登录的官方页面如果无法读到关键条款，来源状态为“官方页面信息不完整”，并提醒用户打开官方渠道确认。

## 3. 用户任务与决策场景

### 3.1 P0：活动与刷卡任务

| 用户任务 | 用户要回答的问题 | 必须提供的记录/状态 |
| --- | --- | --- |
| 保存活动 | 这是什么活动、何时有效、适用于哪张卡？ | 活动标题、卡片、时间窗、规则版本、官方 URL、适用范围、渠道/地区、最后核对日 |
| 核对资格 | 我是否可能符合？官方是否确认？ | `eligibility_status`: `unknown`/`potentially_eligible`/`user_confirmed_eligible`/`user_confirmed_ineligible`/`needs_review`；证据备注和核对时间 |
| 记录报名 | 是否必须报名，报名是否成功，是否有截止日？ | `enrollment_required`、`enrollment_deadline`、`enrollment_status`、官方报名渠道、核对时间 |
| 记录名额 | 是否先到先得、抽签、排名或已分配？ | `quota_allocation`、`quota_status`、名额原文和用户核对结果 |
| 规划消费 | 怎样刷才算，统计发生、入账还是清算？ | 时间窗、`cutoff_basis`、渠道、商户/MCC 排除、币种、附属卡口径、延迟说明 |
| 更新进度 | 截止日前完成但尚未入账，算不算？ | `confirmed_*` 与 `pending_*` 分开；`provisionally_qualified` 不能显示为最终达标 |
| 处理退款 | 退款是否会撤销笔数/金额/奖励？ | 原流水保留，追加负向反向流水；记录规则是否要求重开任务或扣回奖励 |
| 核对奖励 | 达标后什么时候发，是否已到账或被撤回？ | `reward_status`、发放期限原文、到账/撤回日期、争议备注；不得把达标自动改成到账 |

### 3.2 P1：权益、积分与兑换

| 用户任务 | 用户要回答的问题 | 必须提供的记录/状态 |
| --- | --- | --- |
| 维护权益 | 权益是否已下发、剩几次、谁能用？ | 周期、次数/额度、凭证类型、服务商、主附卡/携伴范围、`entitlement_status` |
| 预约及核销 | 预约成功是否等于已使用？现场被拒怎么办？ | `reservation_status`、预约号掩码、`redemption_status`、拒绝/争议原因；只有确认核销才扣减 |
| 录入积分 | 哪个银行/计划、单位是什么、余额何时确认？ | 账户、单位、确认余额、余额日期、来源、有效期模型、最近核对日 |
| 分配批次 | 哪些积分哪天到期，剩余多少无法解释怎么办？ | `PointsLot` 到期日/置信度/用途限制；`unallocated_difference` 显式展示，不自动造批次 |
| 记录兑换 | 兑换了什么，扣分了吗，是否履约？ | 订单/参考号掩码、所需积分、现金部分、履约类型、订单状态、积分扣减状态 |
| 处理失败/退款 | 失败后积分是否已退？实物/里程何时到账？ | 订单和积分状态分离；只有用户确认官方退回后写关联 reversal；保留履约截止和争议 |

### 3.3 P2：增强但不作为首版承诺

- 规则模板库、批量导入、账单/CSV 辅助录入、重复活动检测和版本差异对比。
- 多渠道提醒（邮件、推送）、凭证附件加密保存、家庭/附属卡协作（需重新评估授权和隐私）。
- 由用户确认后的批次扣减建议、价值回顾和跨卡比较；不自动判断“最优卡”、收益或保留/销卡决策。

## 4. 必须显示的未知与待核对状态

任何以下情况不能显示“已完成”“可用”“已到账”或“可兑换”：

| 对象 | 未知/待核对条件 | 页面表现 |
| --- | --- | --- |
| 活动资格 | 页面只写“受邀/符合条件”但用户未在官方渠道确认 | `资格待核对`，不生成确定达标承诺 |
| 报名 | 需要报名但无报名结果、报名截图或官方确认 | `报名状态未知`，任务可以保存但不可标记最终达标 |
| 名额 | 抽签、排名、先到先得或库存未确认 | `名额待核对`，不显示“可参加” |
| 消费口径 | 发生日/入账日/清算日、线上/线下、移动支付、MCC 或排除项未确定 | 任务显示 `口径待核对`，相关流水进入 `pending/unknown` |
| 奖励 | 规则未给发放期限或用户未确认到账 | `奖励待发/未知`，不自动创建收益 |
| 权益凭证 | 卡已激活但服务商未下发凭证 | `待下发`，次数不扣减 |
| 权益使用 | 仅预约或出示，现场未确认核销 | `预约成功/待核销`，不扣减额度 |
| 积分有效期 | 只知道账户总额，没有官方到期日或批次来源 | `到期未知`，不触发到期提醒 |
| 积分差额 | 账户确认余额与流水/批次不一致 | 显示有符号差额并进入 `mismatch`，不自动调整 |
| 兑换扣分 | 订单提交或履约成功但官方账户扣分未知 | 订单与 `points_debit_status` 分开显示 |
| 兑换退分 | 订单失败/取消但银行是否退分未知 | `refund_pending/unknown`，不自动记 reversal |

## 5. 产品实体、字段和状态增量

以下是对当前工作台 PRD 的合并建议，字段名与现有 `docs/PRD-WORKBENCH.md` 保持一致；具体 DDL 由架构/DBA 研究稿决定。

### 5.1 CardActivity（P0）

增加或确认：

`eligibility_status`、`eligibility_verified_at`、`enrollment_required`、`enrollment_deadline`、`enrollment_status`、`enrollment_evidence_note`、`quota_allocation`、`quota_status`、`qualification_basis`、`qualification_delay_text`、`reward_due_rule_text`、`reward_status`、`reward_reversed_on`、`region`、`channel`、`rule_version_id`、`source_id`。

状态必须正交：资格、报名、名额、任务进度、奖励状态互不覆盖；报名成功不等于有名额，任务达标不等于奖励到账。

### 5.2 SpendTask/SpendEntry（P0）

增加或确认：

`cutoff_basis`（occurred/posted/settled/unknown）、`grace_or_posting_delay_text`、`input_mode`（snapshot/entries）、`metric_type`、`confirmed_*`、`pending_*`、`qualified_spend_method_ids`、`exclusions_text`、`include_supplementary_card`、`progress_status`、`evidence_level`、`reconciliation_status`；流水记录发生/入账/清算日期、处理状态、纳入/排除/待核对和 `reversal_of_entry_id`。

`snapshot` 和 `entries` 二选一，不能相加。退款/冲正追加反向流水，不覆盖原记录；跨截止日的退款必须允许任务从达标回退到争议/待核对。

### 5.3 Benefit/BenefitUsage（P1）

增加或确认：

权益周期、下发期限、凭证类型与掩码、服务商、预约渠道、地区/商户/MCC、主附卡及携伴、`entitlement_status`、`reservation_status`、`redemption_status`、拒绝/争议字段。

预约、出示、现场核销是三步；只有 `redemption_status=redeemed` 才减少 `remaining_value`。`pending_delivery`、`rejected`、`disputed` 不得静默扣次数。

### 5.4 PointsAccount/PointsLot/PointsEntry/Redemption（P1）

增加或确认：

- 账户：`confirmed_balance`、`balance_as_of`、`balance_source`、`ledger_balance`、`lots_remaining_total`、`unallocated_difference`、`expiry_model`、`consumption_order`、`reconciliation_status`。
- 批次：`earned_on`、`expires_on`、`expiry_confidence`、`remaining_amount`、`usage_restriction_text`、`origin_type`。
- 流水：`entry_type`（earn/redeem/expire/adjust/transfer/reversal）、`posted_on`、`lot_id`、`reversal_of_entry_id`、`idempotency_key`。
- 兑换：`fulfillment_type`、`fulfillment_deadline`、`points_debit_status`、`status`、`failure_reason`、`refund_expected_on`、`points_returned_on`。

`unallocated_difference = confirmed_balance - lots_remaining_total`。未知到期日不进入提醒；失败不等于退分，只有用户确认退回才写关联 reversal；同一确认使用幂等键避免重复扣减。

## 6. 不属于 Cardfolio 自动化的动作

首版和后续 P1 均明确不自动执行以下动作：

1. 登录银行 App/网银、读取短信/邮箱/账单或保存银行凭据、完整卡号、CVV、身份证件。
2. 代用户判断受邀资格、报名、抢名额、抽签、支付报名费或联系银行客服。
3. 代用户发起消费、选择交易路由、修改支付方式，或根据 MCC/商户名称声称银行已认定某笔交易合格。
4. 代用户预约机场/酒店/服务权益、出示二维码/实体卡、现场核销或向服务商索赔。
5. 自动兑换礼品、里程、酒店积分、账单抵扣或年费；不自动扣减/分配积分批次，不自动假设失败后退分。
6. 把第三方攻略、搜索摘要或过期活动规则更新成当前事实；不自动刷新规则而覆盖历史版本。
7. 根据估算兑换价值推荐办卡、保留/销卡、套现、借贷、投资或税务决策；收益只做用户确认数据的回顾算术。

## 7. 可执行验收标准

### P0 活动与刷卡任务

1. 新建活动时，未填写官方 URL、访问日期、适用期或关键口径，页面将来源标为 `needs_review`，不能显示“可执行达标”。
2. 活动详情同时展示资格、报名、名额、进度和奖励五个状态；修改其中一个状态不改变其他状态，并写入时间线。
3. 活动设置 `enrollment_required=yes` 时，报名状态为 `not_started/submitted/rejected/expired/unknown` 任一，任务都不能进入最终 `qualified`。
4. 资格为 `ineligible/uncertain` 或名额为 `full/not_allocated/unknown` 时，即使用户录入消费已达目标，也只能显示待核对/失败，不显示最终达标。
5. 任务同时显示确定值和待入账值；截止口径为 `posted` 时，只有入账日期落在窗口且流水为 `included` 才进入确定值。
6. `snapshot` 任务不能再叠加 `SpendEntry`；`entries` 任务的汇总可由流水重算，重复提交相同 `idempotency_key` 不产生第二笔。
7. 退款或冲正保留原流水并追加负向关联流水；若退款使累计值低于目标，任务从暂时达标回退并提示核对，不删除原达标历史。
8. 规则未给出发放期限时，达标后奖励显示 `pending/unknown`，不生成预计到账日期；有期限且超过期限才可转 `delayed` 并提醒核对。
9. 奖励到账和奖励撤回分别记录日期、来源和备注；撤回不得静默将历史任务改为未达标。
10. 活动截止、任务截止和奖励核对提醒具有稳定去重键；完成、忽略、稍后处理和逾期状态可恢复并可审计。

### P1 权益、积分与兑换

11. 权益从 `pending_delivery` 到 `available` 必须记录凭证类型、服务商和核对时间；凭证未下发不得显示“可用”。
12. 预约成功但未现场核销时，`remaining_value` 不变；现场拒绝、取消和争议也不扣减次数/额度。
13. 积分账户同时显示用户确认余额、流水余额、批次余额和有符号未分配差额；任一不一致进入 `mismatch`，不自动造批次或调整流水。
14. 批次的到期日为未知时，不创建到期提醒；仅对用户从官方渠道确认且未过期的日期提醒。
15. 兑换订单 `fulfilled` 不自动写积分扣减；只有用户确认官方余额已扣减后才写一条幂等 `redeem` 流水。
16. 兑换失败/取消时保留订单；积分退回未知则为 `refund_pending/unknown`，确认退回后写关联 reversal，重复确认不重复入账。
17. 实物、票券、里程/酒店积分和即时抵扣使用不同 `fulfillment_type`，分别记录履约期限和实际完成日期。
18. 批次带用途限制且不适用于目标兑换时，系统停止建议并要求用户确认，不跳过限制、不自动扣分。
19. 第三方或搜索摘要录入的活动统一显示“线索，待官方核对”，不能预填当前资格、库存、返奖金额或达标承诺。
20. 所有详情页提供来源 URL、来源等级、发布日期/访问日期、适用范围、有效期、最后核对日期和原文摘录；过期规则仍可查看但不产生新提醒。

3. 将用户任务与 P0/P1/P2 表合并到 PRD 的版本范围与用户流程；P0 只承诺活动/任务/奖励闭环，P1 承诺权益/积分/兑换手工账本。
4. 将“必须显示未知”表合并到 PRD 的数据原则、提醒中心和详情页规范，避免空值被 UI 当作已确认。
5. 将 20 条验收标准拆入 PRD 的 P0/P1 验收章节，并由 QA 转成单元测试、状态转换测试和端到端边界用例。

### 8.2 需要架构/DBA 对齐的字段与状态

- `CardActivity`：资格、报名、名额、奖励四条状态轴与任务进度分离；活动规则通过版本和来源引用，不能覆盖历史。
- `SpendTask/Entry`：冻结截止口径和刷卡方式快照；确定/待入账分开；退款只追加反向流水；快照与流水不可双算。
- `Benefit/Usage`：定义、周期额度、预约/使用事件分表；核销才扣减；服务商凭证只保存掩码。
- `PointsAccount/Lot/Entry`：确认余额、流水余额、批次余额和差额均可重算；不自动分配未知批次；流水 append-only、reversal 幂等。
- `Redemption`：订单履约状态和积分扣减状态独立；兑换失败不自动退分；现金部分、参考号和履约期限可审计但不得保存敏感凭据。

### 8.3 仍需人工核对、不能由研究稿定案的结论

- 某张具体卡、某个用户是否受邀/有资格，必须在银行官方 App、活动页或客服确认。
- 当前活动的报名期限、名额、支付渠道、MCC 排除、发奖时点、库存和个人上限，必须随活动原文版本核对；历史来源不替代当前来源。
- 入账/清算日和退款重开规则没有跨银行统一定义；用户需按卡片/活动条款选择口径。
- 权益凭证下发、服务网络、预约、携伴收费和现场容量属于服务商/现场规则；Cardfolio 只记录用户结果。
- 积分到期批次、消费顺序、联名卡积分归属、兑换退分时点和合作方到账时长需要用户从官方账单/账户确认。
- 任何“积分价值”“年费是否值得”“应该办哪张卡”的判断不在本稿范围，必须保持为用户自录算术或后续独立产品研究。
