## 1. 结论

当前年费 MVP 与规划工作台可以共用“卡片为归属、工作台为行动入口、提醒不改变业务事实”的框架，但不能共用一套没有阶段标识的导航或演示数据。当前代码的用户入口仍是“概览 / 我的卡片 / 年费日历 / 提醒中心 / 设置”，API 也只覆盖卡片、年费周期、免年费进度、年费事件和提醒；活动、通用刷卡任务、权益、积分、兑换、统一来源快照均未实现。

本轮 UX 决策如下：

1. 导航、首页模块和快速新增必须按能力可用性渐进出现；不展示不可点击的规划入口，也不以示例卡片暗示已有真实能力。
2. 工作台首屏只回答“现在应处理什么”，不做指标墙。低数据量时保留年费、免年费进度和提醒，不用活动/权益/积分/兑换空卡填充版面。
3. 列表只展示识别、当前最重要事实、紧迫度和一个主操作；详情才展开多状态轴、来源、规则版本和历史。
4. “未知、待核对、处理中、失败、退款、过期、争议”不是一组互斥生命周期。界面必须分别表达事实是否已知、外部流程进展、时间状态和异常原因，不能压成一个综合色点。
5. 活动使用资格/报名/名额/任务进度/奖励五轴；权益使用将下发、预约、核销、额度投影分开；兑换将订单履约与积分处理分开。摘要可折叠，但详情和辅助技术朗读不得丢轴。
6. 来源标签只说明证据类型和新鲜度，不证明个人资格；提醒的完成/稍后/忽略只改变提醒状态，不改变原对象。

## 2. 当前与规划能力的界面边界

所有面向用户的页面、原型、截图、演示和验收记录使用以下三级能力标识；阶段标识属于发布与文档元数据，不应变成每个列表行上的长期徽章。

| 能力层级 | 可出现的位置 | 用户可执行内容 | 禁止表现 |
| --- | --- | --- | --- |
| **当前已实现：年费 MVP** | 正式产品导航、首页、卡片详情、年费日历、提醒中心 | 卡片建档与归档、年费周期、免年费进度、年费事件、年费/进度提醒、导出与账户设置 | 不得写成“完整信用卡工作台已上线” |
| **已定义但未实现：P0/P1** | 研究文档、带明显“概念/规划”标识的原型、验收脚本 | P0 活动/单卡任务/奖励人工核对/来源/站内提醒；P1-a 权益；P1-b 积分与外部兑换记录 | 不进入正式产品导航、快速新增、设置开关或空态引导；不得使用真实可提交按钮 |
| **未来探索：P2** | 路线图和研究说明 | 导入预览后的逐条确认、连接器、自动 lot、系统内预占等经另行评审的能力 | 不以“即将上线”承诺；不出现自动报名、预约、交易、兑换或银行同步动作 |

验收环境应在页面外的构建信息或测试夹具中标明版本；正式年费 MVP 页面无需反复展示“这是 MVP”。当 P0/P1 模块真正通过相应发布门后，再按 feature flag 同时开放导航、深链、搜索分类、快速新增、首页摘要和提醒类型，不能只开放其中一处。

## 3. 导航与首页

### 3.1 导航演进

| 阶段 | 桌面一级入口 | 移动导航 | 说明 |
| --- | --- | --- | --- |
| 当前年费 MVP | 概览、我的卡片、年费日历、提醒中心；设置留在账户区 | 同等入口，不加入空模块 | 保留现有可达性和返回路径 |
| P0 发布后 | 工作台、卡片、活动、提醒；年费日历作为工作台时间线或保留兼容入口 | 只显示已发布入口 | “活动”页内用 `卡活动 / 刷卡任务` 分段；任务不另设一级入口 |
| P1-a/P1-b 发布后 | 工作台、卡片、活动、权益、积分、提醒 | 最多六个业务入口，设置仍在账户区 | 积分页内用 `积分账户 / 到期批次 / 兑换记录` 分段 |

“概览”改名“工作台”时必须保留原深链或可预测重定向。新入口的发布是原子行为：其列表、详情、空态、错误态、返回路径和权限处理全部可用后才显示。移动端不得以横向标签作为发现模块的唯一方式。

### 3.2 首页摘要

首页信息按“需立刻理解的风险 -> 可执行事项 -> 未来日期 -> 低频概况”排序：

1. **行动摘要**：逾期、未来 7 天、待核对、处理中。数字必须可进入带预设筛选的对象列表；同一对象可贡献多个维度，但“待处理总数”必须按对象去重并解释口径。
2. **待处理队列**：桌面最多 6 项，移动首屏建议 3 项后显示“查看全部”。每项包含对象类型、银行/卡片、触发原因、绝对日期加相对时间、当前关键状态和一个主操作。
3. **近期时间线**：默认未来 30 天；同日事件可视觉合并，但每个对象保留独立深链。未知日期的事项不得进入时间线，只能进入“待核对”。
4. **对象摘要**：当前年费 MVP 只显示卡片、年费与免年费进度。P0/P1 发布后才增加进行中任务、临期权益、积分批次和兑换跟进。

首页排序建议固定为：已逾期未处理 -> 7 天内且仍有差距 -> 写入结果未知/处理中超时 -> 规则或来源待核对 -> 30 天内权益/积分到期 -> 90 天内年费 -> 普通维护。同一对象的提醒应聚合，展开后查看触发节点，避免首页和提醒中心重复成两条业务事项。

### 3.3 低数据量状态

- **0 张卡**：只展示“新增第一张卡”一个主操作，并说明会先记录年费与免年费规则；不展示未来模块入口或六块空摘要。
- **1--2 张卡且仅有年费数据**：完整显示现有年费事实、进度和提醒；空余空间留白或显示下一关键日期，不用虚构活动/权益/积分数据补齐网格。
- **有卡但当前无待办**：显示“本周没有待处理事项”和下一条已知日期；提供查看卡片或已完成提醒，不强迫新增规划对象。
- **模块已发布但对象为空**：仅在用户主动进入该模块时显示对象级空态；工作台隐藏该模块摘要。空态给一个动作，不同时要求建活动、权益和积分账户。
- **筛选无结果**：保留筛选条件和总数据存在提示，主操作为“清除筛选”，不得引导新增重复对象。

## 4. 列表与详情信息层级

### 4.1 桌面与移动的共同规则

桌面适合跨对象比较，移动适合快速判断和单项处置。两端共享同一状态、数值、来源、权限和 URL；只改变信息密度和操作容器。

| 层级 | 桌面 | 移动 |
| --- | --- | --- |
| 列表 | 对齐列显示对象、卡片、截止日、主状态、辅助状态、关键数值和主操作 | 三行语义记录：对象+主状态；日期+关键数值；仅异常时显示来源/原因；主操作不依赖侧滑 |
| 详情标题区 | 对象身份、关联卡、主状态、最近日期、唯一主操作；次操作进菜单 | 相同事实单列排列；主操作固定时避开安全区和键盘 |
| 详情正文 | 先结论和影响，再规则、来源、历史；复杂对比可用全宽面板 | 完整页面浏览；一次记录/核对可用底部抽屉，超过一个短任务则转完整页 |
| 横向比较 | 金额、积分、日期列对齐；多状态轴用短摘要加展开 | 不压缩桌面表格；按事实轴纵向排列，提供清晰段标题 |
| 返回与恢复 | 面包屑、筛选 URL、打开检查器前的滚动上下文 | 系统返回和明确关闭均可用；关闭抽屉恢复焦点并保留未提交草稿 |

### 4.2 各对象详情的首屏最小信息

| 对象 | 首屏必须回答 | 深层信息 | 唯一主操作示例 |
| --- | --- | --- | --- |
| 卡活动 | 这是什么、哪张卡、何时结束、资格/报名/名额是否阻断、任务差距、奖励是否已确认 | 五轴时间线、规则条件、多奖励组件、来源版本、历史 | 核对资格 / 记录报名结果 / 核对奖励，按当前阻断选择一个 |
| 刷卡任务 | 目标、确认值、待入账值、剩余量、截止口径、截止日、当前结论 | 计入/排除规则、支付路由、不可变流水、退款/冲正、关联活动和版本 | 更新进度 / 更新入账结果 / 处理退款 |
| 卡权益 | 下发状态、可用范围、剩余量、有效期、是否需预约、最近预约/核销结果 | 使用模型、凭证/服务商、预约轴、核销轴、额度流水、拒绝/争议、来源 | 核对下发 / 记录预约 / 记录使用 |
| 积分账户 | 账户与单位、余额日期、确认余额、流水余额、批次合计、两个差额、最近明确到期批次 | 批次限制、流水、对账历史、来源 | 核对余额 / 补充到期信息 |
| 兑换记录 | 兑换内容、所需积分/现金、订单状态、积分处理状态、提交/预计/实际日期 | 外部参考号掩码、履约时间线、扣分/退分关联流水、来源和争议 | 更新外部结果 / 核对退回 |

列表不可用单一“已完成”概括活动或兑换。活动至少以五轴摘要指出第一个阻断项；兑换必须并列显示“订单状态”和“积分状态”。权益列表至少把下发状态与额度投影分开，预约成功不能使用完成态视觉。

## 5. 统一状态显示规则

### 5.1 四个可并存维度

每个对象按需展示以下维度，避免让一个标签同时回答多个问题：

1. **业务事实**：资格、报名、名额、任务、奖励、下发、预约、核销、订单、积分扣减。
2. **可信度**：已核对、待核对、可能已变化、来源存疑。
3. **时间**：未开始、进行中、即将到期、已过期。
4. **处理与异常**：处理中、失败、退款待核对、已退款、有争议。

列表显示一个业务主状态，最多再显示一个最需要行动的辅助状态；其余状态收进结构化摘要或详情。详情必须写明状态所属维度，例如屏幕阅读器读作“订单状态：成功；积分处理状态：处理中”，不能连续朗读两个无上下文的“成功/处理中”。状态由文字、图标/形状和色彩共同表达；红色只用于真实错误、逾期或高风险变化，橙色用于待核对/临期，蓝色用于一般处理中，绿色只用于已核对的完成事实。

### 5.2 七类关键状态

| 状态语义 | 列表短文案 | 详情必须解释 | 主操作 | 禁止表现 |
| --- | --- | --- | --- | --- |
| **未知** | `资格未知`、`到期未知`、`外部结果未知` | 哪个字段未知、为何未知、最后一次已有证据和未知造成的影响 | 补充信息 / 查看来源 | 不用空白、`--`、0、长期有效或可参加代替；无日期不生成时间线事件 |
| **待核对** | `待核对`，并带对象维度 | 已有线索、缺失证据、最后核对时间、核对后可能影响的状态 | 核对资格 / 核对规则 / 核对余额 | 不等同错误；不以大面积红色警报；不能在未核对时显示确定收益 |
| **处理中** | `待入账`、`奖励待发`、`等待外部结果`、`积分扣减处理中` | 起始时间、最近更新、预计完成依据（若有）、当前不可确认的结果、何时需要人工跟进 | 更新入账结果 / 核对奖励 / 更新外部结果 | 不显示完成勾选；不自动计入确认值；无依据不编预计日期 |
| **失败** | `报名失败`、`兑换失败`、`保存失败` | 失败发生在哪一轴、日期、原因是否经用户核对、已产生/未产生哪些事实 | 记录重新尝试 / 修正并重试 | 不删除原任务或订单；不把外部失败与系统错误混为一谈；不推断积分已退 |
| **退款/冲正** | `退款后重新核对`、`退款待核对`、`已退款` | 原事实、反向事实、金额/积分、证据、当前差距或新有效期是否未知 | 处理退款 / 核对退回 / 查看流水 | 失败或取消不自动显示已退款；不覆盖原流水；只有确认退回后才写“已退款” |
| **过期** | `已过期` 或 `已结束 · 结果待核对` | 过期日期、最终记录、仍需补记的结果、引用的旧规则版本 | 记录过期结果 / 核对奖励 | 不从历史消失；不直接延长旧周期；已确认结果不持续产生提醒 |
| **争议** | `进度有争议`、`奖励有争议`、`使用有争议` | 争议轴、触发事实、证据冲突、最近核对、暂时冻结的结论 | 记录争议 / 核对官方规则 | 不把历史改写成失败；不静默改余额/额度；不只用红色或感叹号解释 |

“未知”表示没有足够事实；“待核对”表示已有信息但需要用户从官方渠道确认。二者可并存为“到期未知 · 待核对来源”，但列表只保留更可行动的“到期未知”，详情再解释可信度。

### 5.3 领域状态投影

#### 活动与任务

- 活动详情固定展示资格、报名、名额、任务进度、奖励五轴，不把 `submitted`、`available`、`target_reached` 或 `expected_pending` 合成“已完成”。
- 只有资格为用户已确认符合、必需报名已确认、名额不阻断、任务本地达标且最终资格已核对时，才可显示“达标待奖励核对”；该文案仍不等于奖励到账。
- `potentially_eligible` 显示“可能符合 · 待核对”，不显示“可参加”；名额 `available` 显示“仍有名额信息”，不显示“已获得名额”。
- confirmed 与 pending 进度同时出现时，主数字使用确认值，待入账值作为独立补充，例如“已确认 5/6 次；另有 1 次待入账”，不能把两者相加后画成绿色达标。
- 退款/冲正后展示原达标快照、反向流水与新差距；当前可转“退款后重新核对/有争议”，历史达标仍可查。

#### 权益

- 详情分别展示下发状态、额度状态、预约状态和核销状态；`pending_delivery` 不计入可用权益。
- “已预约”使用中性处理中视觉并写“待使用”；只有用户确认 `redeemed` 后才能扣减 consumable quota。
- 现场拒绝写“现场未使用 · 服务商拒绝”，保留尝试、时间和原因，不减少次数、不计入已使用价值。
- `coverage_claim`、`fee_credit`、`service_record` 等非次数型权益不展示伪造的“剩余次数”，应展示资格/申请/结果事实；其完整流程未冻结前只能作为规划。

#### 积分与兑换

- 积分账户同屏显示确认余额、流水余额、批次合计、`reconciliation_difference` 和 `unallocated_difference`，每个数带单位与 `as_of`。不得合并差额后称“可用余额”。
- 到期日没有官方或用户确认依据时写“到期未知”，不写“长期有效”，不生成临期提醒。
- 兑换详情固定并列“订单状态”和“积分处理状态”。`success + pending` 显示“订单成功 · 积分扣减处理中”，不能整体显示成功完成。
- `failed/cancelled` 且退分未知时显示“兑换失败 · 积分退回待核对”；只有原扣减事实存在且用户确认官方退回后，才显示“已退款”及关联流水。

## 6. 来源与提醒的可理解性

### 6.1 来源

来源区的最小结构为：`来源类型 + 标题/说明 + 适用范围 + 有效期 + 获取日期 + 最后核对日期 + 可信状态 + 打开原文`。列表仅在异常时显示“待核对/可能已变化/来源存疑”，详情始终可查看完整信息。

| 来源情况 | 用户文案 | 后续动作 |
| --- | --- | --- |
| 官方原文且用户近期核对 | `银行官方规则 · 2026 年 8 月 14 日已核对` | 查看原文/版本 |
| 官方页面缺关键条款 | `银行官方页面 · 关键信息不完整` | 补充官方证据 |
| 第三方或搜索线索 | `活动线索 · 待官方核对` | 在银行官方渠道核对 |
| 超过建议核对周期 | `规则可能已变化 · 上次核对 2026 年 5 月 1 日` | 核对规则 |
| 来源冲突或不可访问 | `来源存疑 · 发现冲突/无法访问` | 比较来源/保留当前记录 |

“银行官方”只是来源类型，不等于用户有资格、当前仍有效或银行已经确认结果。来源原文变化不得静默改写历史任务；详情先展示字段级影响预览，再让用户采用新版本或保留当前记录。

### 6.2 提醒

每条提醒最少回答：`提醒什么对象 + 为什么触发 + 原对象现在是什么状态 + 触发/截止日期 + 下一步`。例如：

> 卡活动 · 奖励待发：经典白金卡活动按当前记录已达标，规则注明 2026 年 9 月 5 日前发放。当前奖励尚未确认。操作：核对奖励。

提醒中心使用 `待处理 / 稍后处理 / 已完成 / 已忽略` 四个视图。完成、稍后、忽略只能改变提醒记录；原对象状态必须在对象详情中单独更新。已忽略提醒可恢复，逾期提醒不会因被看过自动移除。

提醒生成遵守以下规则：

- 活动截止、任务截止和奖励核对是 P0；权益到期、积分到期、兑换跟进只在对应 P1 能力发布后出现。
- 规则无明确奖励日期时，不自动生成“奖励逾期”；可由用户手工设置核对节点。
- 积分批次到期未知时不生成到期提醒；只生成“补充到期信息”的维护项。
- 同一对象、提醒类型和节点去重；归档卡、取消任务、已确认奖励停止未来提醒但保留历史。
- 通知发送失败是送达状态，不回滚业务事实；页面显示最后成功加载/送达时间和局部重试，不把业务对象标为失败。

## 7. 空态、错态与恢复

| 场景 | 页面表现 | 恢复动作 |
| --- | --- | --- |
| 首次空 | 一句当前对象说明、一个主操作；不展示不可用未来模块 | 新增首个当前可用对象 |
| 筛选空 | 保留筛选条件、结果计数和总数据存在提示 | 清除筛选 |
| 已全部处理 | 简短说明和下一已知日期 | 查看已完成 / 返回工作台 |
| 初始加载 | 与最终布局同尺寸的骨架，提供可访问加载文本 | 超时后显示重试 |
| 局部加载失败 | 已加载区继续可用；失败模块说明范围和最后成功时间 | 只重试该模块 |
| 保存校验失败 | 保留输入；错误摘要链接到字段，并写原因与修正方式 | 修正并重试 |
| 网络中断/写入结果未知 | 主操作进入“正在确认”，禁止重复提交；保留草稿和最后成功状态 | 查询上次结果后重试 |
| 无权限/已删除 | 不泄露对象名称、ID、余额或来源 | 返回所属列表/工作台 |
| 已归档/只读 | 顶部只读横幅，历史、规则和流水仍可查看 | 恢复使用（若允许） |
| 部分批量失败 | 显示成功数、失败数和逐项原因，不撤销已成功项除非事务契约如此定义 | 仅重试失败项 |

系统错误、用户输入错误、来源不可信和外部结果未知必须使用不同标题和动作。Toast 只做即时补充，不能成为唯一错误、撤销或待核对信息载体。

## 8. 验收建议

### 8.1 信息架构与发布边界

| 编号 | 场景 | 通过条件 |
| --- | --- | --- |
| UX-FU-01 | 当前年费 MVP | 正式导航和快速新增不出现活动、权益、积分、兑换；页面不宣称工作台 P0/P1 已实现 |
| UX-FU-02 | P0/P1 功能开关 | 某模块只有在列表、详情、空/错态、权限、搜索、提醒和深链同时可用后才出现入口 |
| UX-FU-03 | MVP 低数据量 | 0 张卡只有一个新增主操作；1--2 张卡只显示真实年费/进度/提醒，不出现未来模块空壳 |
| UX-FU-04 | 工作台到详情 | 任一待办在 2 次导航动作内到对应对象和触发记录；刷新后 URL 恢复上下文 |
| UX-FU-05 | 活动与任务归属 | 任务位于活动页分段、工作台或卡片详情，不新增含义重叠的一级入口 |

### 8.2 状态、来源与提醒

| 编号 | 场景 | 通过条件 |
| --- | --- | --- |
| UX-FU-06 | 活动五轴 | 桌面与移动详情分别显示资格/报名/名额/任务/奖励；改变任一轴不把其他轴显示为完成 |
| UX-FU-07 | 未知与待核对 | 未知字段不显示 0、长期有效或可参加；详情说明缺失事实、影响和核对动作 |
| UX-FU-08 | 任务待入账 | confirmed 与 pending 分开；屏幕阅读器能读出维度、数值、目标和剩余 |
| UX-FU-09 | 权益预约/拒绝 | 预约成功不是完成态；拒绝/取消/争议不减少剩余量，保存反馈包含新状态与剩余量 |
| UX-FU-10 | 积分双差额 | 同屏显示确认余额、流水余额、批次合计和两个差额，不合并成“可用余额” |
| UX-FU-11 | 兑换双轴 | `success + pending` 显示订单成功且扣减处理中；失败/取消不显示已退款 |
| UX-FU-12 | 退款/冲正 | 原事实、反向事实、证据和当前影响均可追溯；确认退回前不显示已退款 |
| UX-FU-13 | 过期结果待核对 | 对象进入只读历史但待办仍可深链补记；结果确认后停止未来重复提醒 |
| UX-FU-14 | 争议 | 列表显示具体争议维度，详情保留原快照和冲突证据，不静默改写为失败 |
| UX-FU-15 | 来源可信度 | 官方来源仍显示获取/核对日期；第三方线索不存在“可参加/可用”或自动创建确定任务 |
| UX-FU-16 | 提醒与业务解耦 | 完成/稍后/忽略提醒不改变报名、任务、权益、积分或兑换状态；可打开原对象 |

### 8.3 响应式、错误和辅助功能

| 编号 | 场景 | 通过条件 |
| --- | --- | --- |
| UX-FU-17 | 视口 | 1440、1280、768、390、360 px 无关键字段裁切或横向页面溢出；移动列表不是缩小桌面表格 |
| UX-FU-18 | 单项记录 | 桌面检查器和移动底部抽屉只承载短任务；软键盘不遮主操作，关闭恢复焦点并保留草稿 |
| UX-FU-19 | 网络结果未知 | 重复点击不重复写；界面显示“正在确认上次保存结果”，成功后反馈对象、新值、差距和状态 |
| UX-FU-20 | 局部错误 | 一个摘要失败不清空其他工作台内容；错误说明范围、最后成功时间和局部重试 |
| UX-FU-21 | 非颜色表达 | 七类关键状态均有文字和图标/形状；WCAG AA、高对比和 200%/400% 重排下信息完整 |
| UX-FU-22 | 减弱动效 | 抽屉和状态更新改为短淡入或静态反馈；不因关闭动画或中断操作改变业务事实 |
| UX-FU-23 | 五秒理解测试 | 用户能在 5 秒内区分“暂时达标/奖励待发”“订单成功/扣减处理中”“退款待核对/已退款” |

交互原型应至少使用 0 张、1 张、3 张和 15 张卡四组数据；异常夹具同时包含资格未知、报名失败、待入账、退款重开、权益拒绝、到期未知、余额差额、兑换处理中和退款待核对。桌面测试重点验证比较和深查，移动测试重点验证快速判断、单项记录、返回恢复和软键盘。

## 9. 风险与待决问题

1. 正式文档仍存在旧状态与 canonical 状态并存，例如 `unchecked/eligible`、`pending/expected_pending`、`fulfilled/success`、`points_debit_status/ledger_status`。UX 可定义用户文案，但不能由前端猜测迁移映射；Gate 0 必须先冻结写入状态和兼容读映射。
2. P0 发布后“年费日历”是保留一级兼容入口、并入工作台时间线，还是转为卡片内视图，尚需用现有用户路径和深链数据决定；在决定前不得直接删除入口。
3. 工作台“待处理总数”按提醒条数还是去重对象数尚未冻结。建议主数字按对象去重，详情显示触发节点数，避免同一任务多节点夸大风险。
4. “已结束但奖励待核对”的默认保留期、无发奖期限时的人工核对节奏、来源核对周期和免打扰策略尚未确定，需产品与 QA 给出可测试默认值。
5. 非次数型权益的申请、理赔、年费抵扣和争议状态仍未形成统一契约；在冻结前只能显示为来源备注或规划原型，不应复用次数核销 UI。
6. 多奖励组件、积分两个差额和五轴活动在移动列表上可能过密；需以真实 3--15 张卡数据验证“主状态 + 一个辅助状态 + 详情展开”是否足以理解。
7. 当前产品的卡片详情仍以模态容器承载较多内容；规划中的可深链完整详情页不能描述为现状，迁移时需保留旧入口、返回位置和年费历史。
