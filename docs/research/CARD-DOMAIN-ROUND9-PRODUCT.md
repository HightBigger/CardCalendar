## 1. 研究结论

公开银行页面把“活动入口、支付渠道、权益服务、积分账户和兑换履约”拆在不同产品/服务入口中；因此 Cardfolio 不能以一条卡片状态或一个“积分中心”状态承载全部语义。用户真正需要的是五条相互关联但独立可追溯的记录链：

```text
活动：发现 -> 资格核对 -> 报名 -> 名额/分配 -> 消费达标 -> 奖励组件到账/撤回/争议
权益：适用 -> 凭证下发 -> 可用 -> 预约/出示 -> 现场核销/拒绝/争议
刷卡：规则快照 -> 发生 -> 入账/清算 -> 纳入/排除 -> 退款/冲正
积分：余额观察 -> 批次/到期 -> 用户确认扣减 -> 过期/退回/对账
兑换：预检 -> 提交 -> 订单 -> 履约 -> 扣分/退分 -> 争议
```

每条链都必须保留来源、适用期、最后核对时间和未知原因；“已报名”“已达标”“订单成功”不能自动推导“奖励到账”“积分已扣”或“服务已使用”。

## 3. 需求收敛

### 3.1 用户动作与交付阶段

| 模块 | 用户必须完成的动作 | P0/P1 交付 | 明确不做 |
| --- | --- | --- | --- |
| 卡活动 | 保存来源、核对资格、记录报名/名额、执行任务、核对奖励 | P0：每卡每周期 participation、单卡任务、多奖励组件和人工奖励核对 | 自动报名、抢名额、自动发奖、跨卡合并消费 |
| 卡权益 | 确认下发、预约/改期、记录出示和现场结果 | P1-a：次数型和服务资格型权益；只有确认核销才扣额度 | 代预约、自动核销、把保险/费用抵扣当次数扣减 |
| 刷卡方式 | 选择支付路由和规则口径，记录发生/入账/清算与退款 | P0：激活时冻结 method snapshot，确定/预计进度分离 | 读取银行交易、自动判断银行是否认定合格、个性化最优卡推荐 |
| 积分 | 录入确认余额，补充到期批次，核对流水差额 | P1-b：确认余额、append-only 流水、lot、双差额 | 自动造 lot、静默 FIFO、自动过期、跨账户转移 |
| 积分兑换 | 记录预检、订单、履约、扣分和退分证据 | P1-b：四轴记录，用户确认后幂等 debit/reversal | 自动下单、库存锁定、系统内预占、失败自动猜测退分 |

### 3.2 刷卡方式的统一分类

刷卡方式不是交易流水，而是活动/任务规则的可版本化条件。首版允许用户手工选择或录入以下维度，具体是否计入必须由规则版本决定：

- 交易路由：实体 POS、线上收银台、银行 App、第三方钱包、二维码/移动支付、自动扣款、境外/跨币种、其他/未知。
- 商户范围：指定商户、行业/MCC、线上平台、地区、币种和是否允许附属卡。
- 处理口径：发生日、入账日、清算日、入账延迟、取整方式、最低金额、退款/冲正影响。
- 排除项：取现、转账、分期、手续费、利息、年费、撤销/退货等只能作为规则文本或结构化排除，不得默认跨银行成立。

缺少路由、MCC、截止口径或规则版本时，记录进入 `pending/needs_review`，不进入确定达标值。

### 3.3 权益与积分兑换的分型

- 权益：`consumable_quota`（次数/额度）、`service_eligibility`（服务资格）、`coverage_claim`（保险/理赔）、`fee_credit`（费用抵扣/返还）和 `service_record`（非额度服务）。只有前两类中明确为次数型且首次确认核销时才写 `consume`。
- 兑换：实物/配送、票券/二维码、航空里程/酒店积分、账单抵扣/费用抵扣、公益或其他。每类保存履约渠道、预计/实际完成日期、失败原因和争议入口；订单成功不等于扣分成功。

## 4. 本轮新增验收

1. 同一活动适用两张卡或两个周期时，系统创建独立 participation、任务、奖励和提醒；任一张卡的消费不能改变另一张卡的确定进度。
2. 活动缺少官方来源、适用期、报名口径、支付路由或奖励组件时只能保存为 `lead/needs_review`，不能激活“开始刷卡”提醒。
3. `occurred`、`posted`、`settled` 和 `included/excluded/pending/disputed` 分别展示；规则要求 `posted` 时，只有对应 milestone 落在窗口内才进入确定值。
4. 退款/冲正追加反向事实并保留原始记录；若影响已达标任务或奖励，状态回到 `needs_review`，不删除历史或自动退分。
5. 权益预约、改期、取消、出示和拒绝均不扣次数；只有首次 `redeemed` 写入 `consume`，重复确认返回首次结果。
6. 积分账户同时展示确认余额、账面余额、批次余额、`reconciliation_difference` 和 `unallocated_difference`；差额不为零或批次未知时进入 `needs_review`，不生成到期提醒。
7. 兑换订单、履约、积分扣分和退分状态独立；外部订单成功但扣分未知时显示 `pending_debit`，失败/取消不自动生成 reversal。
8. 所有 unknown/needs_review/disputed 状态必须带 `reason_code`、证据、最后核对时间和 `next_action`；没有明确日期不创建逾期或到期提醒。
