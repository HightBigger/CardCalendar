## 1. 产品定位与术语

### 1.1 定位

Cardfolio 是以“卡片”为核心聚合的个人信用卡管理工作台。它把持卡人分散在银行 App、活动页面、账单、短信和积分商城中的信息，整理成可核对、可提醒、可追溯的个人记录：我有哪些卡、当前有哪些活动/权益、为了达标还需要怎样消费、积分在哪个账户、何时到期、兑换是否完成，以及年费与实际使用价值如何核算。

产品只保存用户主动录入或确认的数据，不连接银行登录、不代管完整卡号、不自动发起交易或兑换。所有规则都带来源、适用范围、有效期和最后核对时间；规则不完整或过期时，产品应显示“待核对”，而不是推断结论。

### 1.2 术语表

| 术语 | 定义与边界 |
| --- | --- |
| 卡片档案（Card） | 用户持有的一张信用卡的非敏感识别与生命周期记录。卡号只允许后四位。 |
| 卡活动（CardActivity） | 银行或合作方在明确时间窗内提供的报名、消费、返积分/返现、礼品或费用减免活动；可关联一张或多张卡。 |
| 卡权益（Benefit） | 卡片固有或随卡提供的服务/额度/次数权益，如机场礼遇、保险、贵宾室、年费减免；不等同于短期营销活动。 |
| 刷卡方式（SpendMethod） | 用户为完成活动或年费条件记录的消费方式/交易口径，例如线下 POS、线上支付、移动支付、境外或指定商户。不是交易流水。 |
| 刷卡任务（SpendTask） | 将活动或年费规则转成可执行的目标，包含时间窗、计数/金额指标、条件关系和排除项。 |
| 积分账户（PointsAccount） | 某家银行/计划下的一种积分余额账本，余额由用户手动录入或调整；不代表银行实时余额。 |
| 积分流水（PointsEntry） | 对积分账户的获得、扣减、过期、调整等记录，可关联活动、消费任务或兑换。 |
| 兑换记录（Redemption） | 用户发起或确认的一次积分/权益兑换，包含商品、渠道、所需积分、订单状态和结果。 |
| 规则版本（RuleVersion） | 在某一生效区间内适用的活动、权益、积分或年费规则快照；规则变更不得覆盖历史版本。 |
| 来源（Source） | 规则原文的 URL、标题、发布/更新时间（如页面提供）、抓取/访问日期、来源等级及原文摘录。 |
| 可信度 | `官方已核验`、`官方页面但信息不完整`、`第三方公开资料`、`用户自录待核对`。可信度不是对规则真实性的保证。 |
| 估算价值 | 用户自行填写的人民币金额或区间，仅用于回顾，不是市场报价、收益承诺或理财建议。 |

### 1.3 通用能力与银行差异

**通用能力**：所有规则实体都支持生效/失效时间、适用卡/客群、地区、渠道、报名要求、指标口径、排除项、名额/预约、来源、最后核对时间和“未知”值；任务支持计数、金额、次数与金额的“同时满足/满足其一/自定义表达式”；积分支持多账户、多单位、分桶有效期和流水；兑换支持库存/资格/渠道限制和订单状态。

**银行差异**：积分单位、累计比例、取整方式、入账时点、有效期、消费排除项、年费周期、权益次数和兑换门槛均由银行/卡种/活动决定。系统不能把任何一家银行的具体数值当作默认规则，也不能用一条规则覆盖同一银行的不同卡种。用户未提供原文时，字段显示“未确认”。

## 2. 用户画像、目标与非目标

### 2.1 用户画像

1. **多卡管理者（主画像）**：持有 3--15 张个人卡，跨多家银行；每月或每季度更新一次记录，重点关注年费、消费达标、活动截止日和积分到期。
2. **权益使用者**：持有高端或联名卡，权益价值取决于次数、预约、指定渠道或有效期；需要知道“可用、已用、即将过期、需要预约”。
3. **积分规划者**：有多个积分账户，定期兑换礼品、里程或抵扣；需要看余额、批次到期和已兑换结果，不要求自动下单。
4. **轻度持卡人**：持有 1--3 张卡，只需要快速录入和关键日期提醒。

不服务企业卡、家庭共享账本、代他人管理账户或需要银行自动同步的用户（后续若扩展需重新评估授权与隐私模型）。

### 2.2 产品目标

- 首次登录后 3 分钟内完成首张卡和一个关键提醒的录入。
- 用户打开工作台即可看见未来 90 天的年费、活动、权益、积分到期和待完成任务。
- 用户能把一条规则拆成可核对的任务，看到当前值、目标值、剩余值、截止日和证据。
- 用户能追溯每个余额、兑换和收益数字的来源与修改历史。
- 对规则不确定、已过期、渠道受限的情况明确提示，降低错过权益或错误刷卡的风险。

### 2.3 非目标

- 不读取银行 App、网银、短信、邮箱或账单，不保存登录凭据、完整卡号、CVV、密码或身份证号。
- 不自动判断某笔交易是否符合银行规则，不自动承诺返现/积分/免年费，不提供授信、投资、借贷或税务建议。
- 不代用户报名、支付、兑换、预约或联系银行；不做家庭共享、企业报销和实时资产净值。
- 不将公开活动规则当作对用户个人资质的确认；所有资格需用户在银行官方渠道自行确认。

### 2.4 成功指标

指标以用户主动确认的数据为分母，不以银行实际发奖或资格作为 Cardfolio 可控结果：

- **建档完成率**：首次创建卡片的用户中，7 日内至少补齐一个活动/权益/任务/积分账户及来源的比例不低于 50%。
- **规则可核对率**：活跃活动、权益和任务中，具有官方来源、适用期、最后核对时间的对象比例不低于 80%。
- **临期处置率**：到期前 30 天内产生提醒的对象中，在截止日前被标记完成、已核对或明确忽略的比例不低于 70%。
- **任务对账率**：到期任务中具有用户最终核对结果（达标/未达标/有争议）的比例不低于 60%。
- **积分新鲜度**：活跃积分账户中，余额核对日期在用户设定周期内的比例不低于 70%；不使用“余额准确率”作为指标，因为 P0 无银行实时数据。
- **错误恢复率**：发生退款、冲正、兑换失败/退款的测试样本中，100% 保留原流水并通过反向记录恢复可重算余额。

## 3. 工作台信息范围与数据原则

### 3.1 首页工作台

默认时间窗为未来 90 天，可切换 30/180/365 天。首页包含：

- **待处理总览**：即将到期的年费事件、活动截止、权益到期、积分批次到期、逾期任务数。
- **任务进度**：按“截止日、剩余量、规则可信度”排序，显示当前值/目标值/剩余值和条件关系。
- **卡片摘要**：使用中/待核对/已归档卡片数，最近核对日期，下一年费日。
- **积分摘要**：按账户显示用户录入余额、最近到期批次和最近兑换结果；不显示“实时”字样。
- **收益摘要**：按自然年或自定义期间汇总已确认年费、用户确认的权益价值、积分兑换价值和净值；估算项单独标识。
- **提醒中心入口**：未处理、稍后处理、已完成、已忽略，并可按对象类型筛选。

每个摘要卡片必须能下钻到对象详情；没有来源或最后核对超过用户设定阈值时，显示“请核对官方规则”。

### 3.2 数据记录原则

- 规则文本以版本快照保存，编辑产生新版本；历史任务和流水引用原版本。
- 金额统一保存数值、币种和精度；积分保存数量、单位和账户，不隐含兑换比例。
- 所有日期带用户时区解释；跨日和夏令时由统一日期库处理。
- 用户录入与系统计算分离：原始值可审计，计算值可重算；删除优先使用归档/作废而非物理删除。
- 规则字段允许 `unknown`，不可用前端默认值填充为事实。

## 4. 实体字段与状态

以下字段为开发契约，`id`、`created_at`、`updated_at`、`owner_user_id` 为所有实体必备；金额/数量禁止使用浮点。

### 4.1 卡片档案 Card（P0）

**字段**：`issuer_name`、`product_name`、`network`（银联/Visa/Mastercard/Amex/其他/未知）、`tier`、`last4`（四位数字）、`currency`、`annual_fee_amount`、`annual_fee_rule_id`、`opened_on`、`activated_on`、`billing_day`、`annual_fee_cycle_type`（激活首账单日/开卡日/固定日期/自定义/未知）、`next_annual_fee_on`、`status`（active/suspended/closed/archived）、`last_verified_on`、`source_id`、`notes`。

**约束**：不接收完整卡号/CVV；`last4` 可选但若填写必须为 4 位数字；年费和币种可为未知；归档卡保留历史但停止新提醒和新任务。

### 4.2 规则来源 Source 与规则版本 RuleVersion（P0）

**Source 字段**：`url`、`title`、`publisher`、`published_on`（未知可空）、`accessed_on`、`source_level`（官方规则/官方商品页/官方商城/监管或协会/成熟产品公开说明/第三方）、`excerpt`、`content_hash`（防止静默替换）、`notes`。

**RuleVersion 字段**：`rule_type`（annual_fee/activity/benefit/spend/points/redemption）、`object_id`、`effective_from`、`effective_to`、`eligibility_text`、`region`、`channel`、`registration_required`、`booking_required`、`quota_text`、`exclusions_text`、`status`（draft/active/expired/superseded/needs_review）、`source_id`、`verified_by_user_at`。

规则版本必须可并存；新规则生效后，旧版本进入 `superseded`，历史记录仍指向旧版本。

### 4.3 卡活动 CardActivity（P0）

**字段**：`title`、`issuer_name`、`activity_type`（消费返积分/返现/礼品/年费减免/报名权益/其他）、`applicable_card_ids`、`eligibility_text`、`start_at`、`end_at`、`enrollment_deadline`、`enrollment_status`（not_required/not_started/enrolled/failed/unknown）、`enrollment_verified_at`、`reward_type`、`reward_amount_text`、`reward_cap_text`、`quota_allocation`（unlimited/first_come/ranking/lottery/unknown）、`qualification_basis`（交易发生日/入账日/清算日/其他/未知）、`qualification_delay_text`、`expected_reward_on`、`reward_status`（not_expected/pending/received/reversed/disputed/unknown）、`settlement_on`、`region`、`channel`（线下/线上/移动支付/指定 App/指定商户/未知）、`quota_text`、`rule_version_id`、`status`（planned/running/ended/cancelled/needs_review）、`notes`。

活动不把奖励金额解析成通用数值，除非来源明确且用户确认；超出上限、报名失败和名额不足需能单独记录。

### 4.4 卡权益 Benefit（P0）

**字段**：`card_id`、`name`、`benefit_type`（次数/额度/保险/贵宾室/服务/费用减免/其他）、`period_type`（自然年/持卡年/账单周期/月/一次性/自定义）、`valid_from`、`valid_to`、`quota_value`、`quota_unit`、`used_value`、`remaining_value`、`entitlement_status`（pending_delivery/available/suspended/expired/unknown）、`delivery_due_on`、`service_provider`、`credential_type`（实体卡/二维码/会员号/预约确认/无需凭证/未知）、`requires_booking`、`booking_channel`、`eligible_region`、`merchant_or_mcc_text`、`holder_scope`（主卡本人/附属卡/可携伴/未知）、`companion_cost_text`、`activation_required`、`usage_status`（available/partially_used/used/expired/blocked/disputed/unknown）、`estimated_value_amount`、`estimated_value_currency`、`actual_value_amount`、`source_id`、`last_verified_on`、`notes`。

**BenefitUsage 字段**：`benefit_id`、`planned_on`、`booked_at`、`used_at`、`quantity`、`location_or_provider`、`status`（planned/booked/used/rejected/cancelled/disputed）、`actual_charge_amount`、`currency`、`rejection_reason`、`note`。预约成功不等于已使用；现场拒绝、容量限制、权益暂停或额外扣费不得自动减少额度，须由用户确认。

额度/次数为用户维护的记录，不从“权益存在”推断“可用”；预约、地区、渠道和附属卡资格必须在详情中可见。

### 4.5 刷卡方式 SpendMethod 与刷卡任务 SpendTask（P0）

**SpendMethod 字段**：`name`、`channel_type`（POS/电商/银行 App/第三方钱包/二维码/境外/自动扣款/其他）、`merchant_scope`、`region_scope`、`currency_scope`、`mcc_or_exclusion_text`、`evidence_note`、`status`。

**SpendTask 字段**：`card_id`、`activity_id`（可空）、`task_type`（年费达标/活动达标/权益解锁/自定义）、`period_start`、`period_end`、`cutoff_basis`（occurred/posted/settled/unknown）、`grace_or_posting_delay_text`、`metric_type`（count/amount/count_and_amount/count_or_amount/custom）、`target_count`、`target_amount`、`currency`、`condition_relation`（all/any/custom）、`current_count`、`current_amount`、`pending_count`、`pending_amount`、`remaining_count`、`remaining_amount`、`qualified_spend_method_ids`、`exclusions_text`、`include_supplementary_card`（yes/no/unknown）、`progress_status`（not_started/in_progress/provisionally_qualified/qualified/failed/expired/disputed/needs_review）、`evidence_level`（user_total/user_entries/bank_confirmed/unknown）、`reconciliation_status`（not_due/pending/reconciled/disputed）、`rule_version_id`、`last_reconciled_on`。

**SpendEntry 字段**：`task_id`、`occurred_on`、`posted_on`、`settled_on`、`entry_status`（pending/posted/settled/reversed/rejected/unknown）、`count_delta`、`amount_delta`、`currency`、`method_id`、`qualification_status`（included/excluded/pending/disputed/unknown）、`reversal_of_entry_id`、`note`。系统只记录用户汇总或手工增量，不声称交易已被银行认定；未入账交易计入 `pending_*` 而非已达标值，退款/冲正必须以负向流水保留关联。

### 4.6 积分账户 PointsAccount、积分流水 PointsEntry（P0）

**PointsAccount 字段**：`issuer_name`、`program_name`、`card_id`（可空，支持同银行合并池）、`points_unit`、`balance`、`balance_as_of`、`balance_source`（user_input/bank_statement/official_app/other）、`expiry_model`（none/fixed_date/rolling/lot_based/unknown）、`default_expiry_text`、`consumption_order`（earliest_expiry_first/issuer_defined/user_selected/unknown）、`reconciliation_status`（balanced/mismatch/pending/unknown）、`unallocated_balance`、`status`（active/frozen/closed/needs_review）、`source_id`、`last_verified_on`。

**PointsLot 字段**：`account_id`、`earned_on`、`expires_on`、`expiry_basis`（fixed/rolling/activity_specific/unknown）、`expiry_confidence`（official/user_input/inferred/unknown）、`amount`、`reserved_amount`、`remaining_amount`、`usage_restriction_text`、`origin_type`（spend/activity/manual/adjustment）、`origin_id`、`status`（open/partially_used/reserved/used/expired/void/disputed）。

**PointsEntry 字段**：`account_id`、`entry_type`（earn/redeem/expire/adjust/transfer/reversal）、`amount`、`occurred_on`、`posted_on`、`lot_id`（可空）、`reference_text`、`source_id`、`note`。

积分有效期默认 `unknown`；不能因某家银行“长期有效”或“固定年限”而给所有账户预填规则。到期提醒只针对用户录入的 `expires_on` 或明确来源规则。

### 4.7 兑换记录 Redemption（P0）

**字段**：`account_id`、`card_id`（可空）、`catalog_name`、`item_name`、`redemption_type`（商城商品/里程/酒店积分/账单抵扣/年费/其他）、`order_or_reference_no`（不得填完整卡号）、`channel`、`requested_on`、`required_points`、`cash_component_amount`、`currency`、`eligibility_text`、`quota_text`、`fulfillment_type`（instant_credit/voucher/physical_delivery/manual_review/unknown）、`fulfillment_deadline`、`points_debit_status`（not_debited/reserved/debited/reversed/unknown）、`status`（planned/submitted/processing/success/failed/cancelled/refund_pending/refunded/disputed/unknown）、`failure_reason`、`fulfilled_on`、`refund_expected_on`、`actual_value_amount`、`source_id`、`note`。

兑换比例、库存、每户上限和渠道资格从来源带入；没有来源时只能记录用户实际兑换，不展示推荐排序。

### 4.8 提醒 Reminder 与收益记录 ValueRecord（P0/P1）

**Reminder 字段**：`object_type`、`object_id`、`trigger_at`、`timezone`、`reminder_type`（annual_fee/activity_end/benefit_expiry/task_due/points_expiry/verification_due）、`status`（pending/snoozed/completed/ignored/overdue/cancelled）、`delivery`（in_app，P1 email/push）、`completed_at`、`snoozed_until`、`dedupe_key`。

**ValueRecord 字段**：`card_id`、`period_start`、`period_end`、`fee_amount`、`fee_waived_amount`、`benefit_actual_value`、`benefit_estimated_value`、`points_value`、`cashback_value`、`other_cost_amount`、`net_value_amount`、`currency`、`confidence`（confirmed/estimated/user_input）、`calculation_note`、`source_id`。`net_value_amount` 只做算术汇总，不能表述为预期收益。

## 5. 功能需求与优先级

### 5.1 P0：MVP 工作台

- 账号、时区、数据导出/账户删除沿用现有 PRD 的 P0 要求。
- 卡片档案新增上述字段，支持使用中/暂停/已关闭/已归档，归档保留历史。
- 手动录入活动、权益、刷卡方式和任务；任务支持次数、金额、同时满足/满足其一、截止日、排除项和证据等级。
- 活动报名、任务进度、奖励到账必须分离；P0 支持预计/已入账进度、退款反向流水和人工争议状态，不负责自动认定交易。
- 权益下发、预约、使用、拒绝/争议必须分离；P0 只记录用户确认结果，不代用户预约或向第三方发送个人信息。
- 手动维护积分账户余额、批次到期日和积分流水；支持年费、商城、里程等兑换记录。
- 积分总额与批次合计允许暂时不一致并显示差额；P0 由用户指定批次扣减或记录未分配余额，不自动跨用途限制分配。
- 首页按 90 天时间窗汇总年费、活动、权益、任务、积分到期与待核对规则。
- 站内提醒：默认提前 30/7/1 天仅适用于年费；活动/权益/积分由用户选择节点；支持稍后处理、完成、忽略和逾期。
- 每个规则对象显示来源等级、原文链接、发布日期/访问日期、适用范围、最后核对日期和“待核对”状态。
- 收益核算展示用户输入的已确认/估算分项与计算过程，不输出保留/销卡建议。

### 5.2 P1：提高维护效率

- 常用银行/卡种模板，但模板只预填字段结构和来源链接，不预填未经核验的数值。
- CSV/JSON 导入导出、批量编辑、重复规则检测、规则版本对比。
- 按明确的 `consumption_order` 自动建议批次扣减顺序、权益使用历史筛选、奖励逾期对账清单；任何建议都需用户确认。
- 本地账单 PDF/短信解析预览，必须用户逐条确认后才写入 SpendEntry/PointsEntry。
- 邮件、浏览器 Push 提醒和免打扰时段；提醒失败不影响原始对象。
- 权益使用凭证（用户上传的非敏感截图或备注）和兑换订单附件，默认本地加密/短期保留策略待安全评审。

### 5.3 P2：谨慎探索

- 可撤销、最小权限的第三方账单同步；不保存银行密码，授权范围与供应商合规另行评审。
- 规则变更订阅、差异摘要和用户确认工作流；不自动将变化应用到历史任务。
- PWA 离线查看、快捷录入和多设备同步。
- 基于历史记录的“信息性比较视图”（费用与实际使用情况），不生成个性化金融建议或收益预测。

## 6. 关键用户流程

### 6.1 首次建档

注册/登录 -> 设置时区 -> 新增卡片（银行、卡名、后四位、激活/账单日、年费） -> 选择“规则未知/手动录入/粘贴官方来源” -> 保存卡片 -> 添加年费任务和提醒 -> 可选添加首个活动、权益或积分账户。

### 6.2 录入并执行活动

活动列表 -> 新增活动 -> 填写时间窗、适用卡、报名/预约、渠道、地区、指标和排除项 -> 关联或创建 SpendTask -> 记录手工累计/增量 -> 系统计算进度 -> 用户在银行官方渠道核对 -> 标记 `qualified` 或 `needs_review`。

### 6.3 维护权益

卡片详情 -> 权益 -> 录入额度/次数、有效期、预约渠道和估算价值 -> 每次使用记录日期与使用量 -> 余额减少 -> 到期前提醒 -> 过期后只读保留。

### 6.4 积分到期与兑换

积分中心 -> 选择账户 -> 录入余额或导入用户自己的账单摘要 -> 按批次维护到期日 -> 到期前提醒 -> 用户在银行官方商城/APP兑换 -> 记录渠道、所需积分、订单状态和实际价值 -> 成功后生成扣减流水并关联批次；失败/退款不得静默删除。

### 6.5 规则变更

用户打开来源链接核对 -> 新建 RuleVersion -> 填写生效区间和变化摘要 -> 旧版本标记 `superseded` -> 未开始任务可选择迁移，进行中/已完成任务保持原版本并提示重新确认。

### 6.6 异常与争议处理

1. **活动未报名/报名失败**：活动仍可收藏和展示，但任务不得显示“可达标”；用户需记录报名渠道、结果和核对时间。报名截止后状态进入 `failed` 或 `unknown`，不自动删除任务。
2. **交易发生但未入账**：先计入 `pending_count/pending_amount` 并显示“预计进度”；只有用户确认银行已入账/清算且符合口径后，才能进入确定进度。截止日经过仍未入账则进入 `disputed` 或 `failed`，不由系统猜测。
3. **退款/冲正跨周期**：以反向 SpendEntry 关联原记录；如果影响已关闭任务，重新打开为 `disputed` 并保留此前达标快照和变更原因。
4. **奖励迟到或被撤回**：任务达标与奖励到账分开；活动 `reward_status` 可独立处于 `pending/received/reversed/disputed`。超出规则所述发放时间后才提醒用户核对。
5. **权益未下发/现场拒绝**：权益可处于 `pending_delivery`，服务商未发凭证或现场容量限制时记录 `rejected/disputed`；未实际使用不得扣减次数，额外收费需用户确认。
6. **积分总额与批次不一致**：账户保存官方/用户确认总额，无法归入批次的差额进入 `unallocated_balance`；系统不得为差额虚构到期日。核对后以调整流水修正。
7. **兑换失败、超时或退款**：P0 只记录用户在外部渠道的计划、提交、到账和结果；只有用户确认兑换成功才写一次幂等扣减流水。失败不自动假定积分已退，只有确认退回才写反向流水。系统内积分预占和自动履约属于 P1/P2；实物配送、票券入账和里程到账使用不同履约状态。

## 8. 功能验收标准

### 8.1 P0 验收

1. 新用户能在单一表单创建卡片；保存后只在数据库、日志和导出中出现后四位，不接受完整卡号、CVV、密码或银行凭据。
2. 卡片详情可同时展示年费周期、活动、权益、刷卡任务、积分账户和兑换记录；任何对象缺来源时明确标记 `needs_review`。
3. 任务支持 `count`、`amount`、`count_and_amount`、`count_or_amount` 和 `custom`；输入累计值或增量后正确计算当前/目标/剩余，负数和币种不一致被阻止或要求确认。
4. 任务能记录渠道、地区、商户范围、排除项、附属卡是否计入和退款/冲正；系统不声称已自动验证银行认定结果。
5. 活动、权益和积分批次按各自截止日生成站内提醒；同一对象同一节点不重复生成；完成/忽略/稍后处理可追溯。
6. 积分账户支持多个单位和批次；余额、获得、兑换、过期、调整可重算，批次耗尽/过期状态正确，未知有效期不会生成虚假到期日。
7. 兑换记录支持商城商品、里程、酒店积分、年费等类型，能保存渠道、资格限制、所需积分、现金补差和失败/退款状态。
8. 规则版本可新增、失效和替代；历史任务/流水仍指向原版本，规则变化不覆盖历史。
9. 收益页展示年费、减免、权益实际/估算价值、积分价值和净值的算术过程，并区分 `confirmed`/`estimated`；页面显示“仅供记录，不构成金融建议”。
10. 首页 90 天视图、卡片详情、活动、任务、积分和提醒中心可互相跳转；移动端 360 px 以上无横向溢出。
11. 服务端执行用户所有权校验；归档卡停止新提醒但保留历史；导出和账户删除需要二次确认并写审计记录。

### 8.2 P1/P2 验收门槛

- 导入必须预览、逐行校验、可下载错误行，失败不产生部分隐式写入。
- 解析或同步产生的每个字段必须显示“待用户确认”，并能撤销授权/删除同步数据。
- 规则差异摘要必须展示新旧来源和生效日，不能自动重算已完成任务。

### 8.3 第二轮边界验收

1. 活动设置“必须报名”后，`not_started/failed/unknown` 均不允许将任务标为 `qualified`；用户确认 `enrolled` 后才开放进度确认。
2. 同一任务录入一笔 `pending` 交易时只增加预计进度；切换为 `posted/settled` 后才增加确定进度；切换为 `reversed` 后通过关联反向流水扣回且审计历史完整。
3. 同时满足次数和金额的任务，任一条件只达到预计值时显示 `provisionally_qualified`，不能显示银行已确认达标。
4. 活动任务达标后，奖励仍可为 `pending`；到达预期发放日未到账时生成核对提醒，奖励撤回不会静默改写任务历史。
5. 权益从 `pending_delivery` 到 `available` 需记录凭证/服务商和核对时间；预约后取消、现场拒绝或争议均不减少 `remaining_value`，只有 `used` 才扣减。
6. 积分账户余额与批次合计不一致时显示差额并进入 `mismatch`；未知差额不分配到任何到期批次，也不触发虚假到期提醒。
7. 批次设置“最早到期优先”时，P0 仅展示建议扣减批次并要求用户确认，不自动分配；若该批次带用途限制而不适用于当前兑换，则停止建议并要求用户确认，不能跳过限制静默扣分。系统内预占属于 P1/P2。
8. 兑换 `failed/refund_pending` 时保留订单和积分处理状态；只有记录积分退回后生成 reversal 并转为 `refunded`，账户与流水可重算一致。
9. 已结束任务因跨周期退款重新进入 `disputed` 时，原结束状态、发生时间、触发退款和修订后的进度均可查看。
10. 所有搜索发现或第三方整理的活动必须显示“线索，待官方核对”，不得自动填充为当前可参加资格或创建达标承诺。

## 9. 非功能、隐私与安全

### 9.1 安全与隐私

- 数据最小化：只收集实现工作台所需的银行、卡名、后四位、日期、用户手工金额/次数和来源；默认不收集交易明细、商户、地理位置、身份证件、完整卡号、CVV、密码或银行登录信息。
- 字段级校验、服务端所有权校验、CSRF/Origin 校验、速率限制、成熟密码慢哈希、会话过期和 HTTPS 为上线前置条件。
- 日志和错误追踪脱敏；禁止把来源页面中的用户参数、订单号或可识别信息写入分析事件。
- 导出、删除、归档、授权和规则确认均写入审计时间线；账户删除提供可撤销冷静期或明确不可恢复提示，具体保留期由合规评审确定。
- 用户上传的凭证（P1）默认不公开、不用于训练或推荐；文件类型、大小、恶意内容和保留期限须单独评审。

### 9.2 性能、可用性与可访问性

- 首页/详情常规网络下首屏可交互不超过 2 秒，接口 p95 不超过 500 ms；单用户支持至少 100 张卡片、每卡 10 年历史记录。
- 日期计算统一使用用户时区；计算、提醒和规则版本有单元测试，主流程有端到端测试。
- 关键状态不只用颜色表达；表单标签、错误和提醒可被屏幕阅读器读取，支持键盘和 360 px 以上移动端。
- 服务异常不得重复生成提醒、流水或年费事件；写入使用事务和幂等键。

### 9.3 “不构成金融建议”边界

产品只展示用户输入和来源规则的结构化记录、状态与算术汇总，不判断应否申请、保留、降级、销卡、套现、借贷或投资，不承诺积分价值、返现、免年费资格或未来收益。所有“推荐”文案统一改为“记录/比较/待核对”，并在收益、任务和兑换页面固定展示：

> 本工具仅用于个人信息记录和计算，不构成金融、投资、信用、税务或法律建议。银行规则、资格、交易入账及兑换结果以发卡行或活动主办方最新官方说明为准。

### 10.2 关键决策

1. **卡片为核心聚合**：活动、权益、刷卡任务、积分账户和兑换记录独立建模并关联卡片，避免把银行差异堆进卡片表。
2. **规则可追溯而非自动推断**：每条规则必须有来源、版本、适用范围、生效期、渠道/排除项和最后核对日期；缺字段即待核对。
3. **数值不泛化**：官方来源中的具体笔数、金额、积分比例只作为实例或用户自录规则，绝不生成跨银行默认值。
4. **收益只做回顾**：净值是用户输入分项的算术结果，分离估算与已确认，不输出金融建议。
5. **手动优先、授权后置**：P0 不接银行；未来解析/同步必须预览、确认、可撤销和最小化保存。

### 10.3 研究限制与风险

- 银行页面可能按年度、卡种、客户等级或地区变化；本 PRD 的银行事实不代表 2026 年之后仍有效。
- 部分积分商城/活动页需要登录或动态脚本，无法仅凭公开页面验证个人资格、库存或实时余额；产品必须允许“官方页面但信息不完整”。
- 搜索摘要或历史 PDF 只能证明页面存在及其公开表述，不能替代用户当前账单/银行 App 的最终结果；历史规则不得自动套用到新卡。
- 第三方成熟产品的功能说明用于启发信息架构，不作为银行规则证据，也不暗示 Cardfolio 具备其自动化能力。
- 任何自动同步、OCR、文件上传和推送能力在实现前需进行隐私、安全、合规和误判率评审。

## 11. 第二轮调研与需求修订

### 11.1 复核结论

第二轮围绕卡活动、卡权益、刷卡方式/任务、积分账户/到期批次/兑换复核。结论是：第一轮实体方向正确，但将“任务完成”视作单一状态不足以覆盖真实规则。官方规则显示至少存在五条相互独立的状态链：

```text
活动：发现 -> 核对资格 -> 报名 -> 交易达标 -> 奖励待发 -> 奖励到账/撤回/争议
权益：等待下发 -> 可用 -> 预约 -> 现场核销 -> 已用/拒绝/争议
交易：发生 -> 待入账 -> 已入账/清算 -> 符合/排除 -> 退款/冲正
积分：账户总额 -> 到期批次/未分配差额 -> 预占 -> 扣减 -> 退回/过期
兑换：计划 -> 提交 -> 处理 -> 不同履约方式 -> 成功/失败/退款/争议
```

因此本轮把状态拆分为 `enrollment_status`、`progress_status`、`reward_status`、`entitlement_status`、`usage_status`、`entry_status`、`qualification_status`、`points_debit_status` 和 `redemption.status`。开发不得用一个“完成”字段替代这些状态。

### 11.2 新增用户场景

- 用户从公开页面发现活动，但不确定本人是否受邀：先保存为“线索”，只在银行官方渠道核对后转为可执行活动。
- 用户报名成功后才消费；如果报名失败、名额用尽或活动已截止，保留记录用于复盘，不提示继续刷卡。
- 用户截止日前完成消费但交易尚未入账：展示预计进度和风险，不提前宣布达标。
- 用户已达标但奖励未按期到账，或到账后因退款被撤回：独立跟踪奖励状态和争议时间线。
- 用户激活卡片后权益凭证延迟下发，或预约成功但现场因容量/服务网络变更被拒：不把权益误记为已用。
- 用户只知道积分总额和一个临近到期批次，无法解释剩余积分：保留未分配差额，不伪造批次。
- 用户兑换时存在最早到期批次，但该批次不可用于目标商品/里程：停止自动扣分并要求人工确认。
- 用户兑换失败但积分是否退回未知：订单与积分扣减分别保留待核对状态。
